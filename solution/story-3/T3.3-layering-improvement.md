## 1. Goal

Validate whether Dockerfile layer reordering improves same-daemon warm-cache rebuild behaviour after application artefact changes, without changing base image, package list, `envconsul` version, Maven lifecycle, `CMD`, debug/JMX settings, healthcheck, entrypoint or runtime behaviour.

T3.3 is not primarily a cold-build optimisation task. On a no-cache build, the `yum`/install/`envconsul` layer still runs and is expected to remain dominant. The main measurement question is:

```text
If only the application JAR changes, can Docker reuse the expensive yum/envconsul/user setup layer?
```

The intended target claim is limited to:

```text
Layer ordering may improve same-daemon warm-cache rebuild behaviour after application artefact changes.
```

Do not claim a general Docker build improvement, CI saving, image-size reduction or production Dockerfile recommendation from T3.3 before measurement and ownership confirmation.

## 3. Selected Candidate

The selected T3.3 candidate is a layer-order prototype that preserves the current packaging lifecycle:

```text
Maven build produces target artefacts -> Dockerfile packages the JAR and OpenTelemetry agent
```

The prototype should move expensive, rarely changing setup before application artefact copies:

1. keep the current runtime base image;
2. run package/`envconsul`/user setup before copying the JAR;
3. copy the OpenTelemetry agent and application JAR late;
4. keep post-copy ownership/permission work small and limited to copied artefacts;
5. measure current vs prototype warm-cache rebuild behaviour before recommending anything for RepoSync.

This avoids changing Java distribution, operating-system family, Maven build lifecycle, runtime entrypoint, debug/JMX defaults or base-image source in the same task.

## 4. Prototype Dockerfile Shape

Create the prototype separately from the production Dockerfile:

```text
cmd-adaptor-sns/Dockerfile.layer-order-prototype
```

This is a local prototype shape, not a committed production Dockerfile replacement:

```dockerfile
FROM amazoncorretto:17

WORKDIR /tmp

# Expensive setup first. This layer changes rarely and can be reused in local/same-daemon cached builds.
RUN yum install -y shadow-utils unzip \
    && yum update -y ca-certificates cpio curl cyrus-sasl-lib expat glib2 \
       libcurl libdb libssh2 libdb-utils libnghttp2 libpng libtasn1 libxml2 \
       ncurses ncurses-base ncurses-libs nss nss-util nss-softokn nspr \
       openldap openssl-libs python python-libs sqlite xz-libs yum zlib \
    && yum erase -y vim-data \
    && yum clean all \
    && rm -rf /var/cache/yum \
    && curl --silent --output /tmp/envconsul.zip \
       https://releases.hashicorp.com/envconsul/0.13.1/envconsul_0.13.1_linux_amd64.zip \
    && unzip envconsul.zip \
    && rm -f envconsul.zip \
    && mv envconsul /usr/local/bin/envconsul \
    && chown root:root /usr/local/bin/envconsul \
    && chmod 0755 /usr/local/bin/envconsul \
    && adduser -u 1000 -U -m -s /bin/bash fdpuser

# Frequently changing runtime artefacts last.
COPY ./target/cmd-adaptor-sns-exec.jar /local/cmd-adaptor-sns-exec.jar
COPY ./target/dependencies/opentelemetry-javaagent.jar /local/opentelemetry-javaagent.jar

RUN chmod 0755 /local/cmd-adaptor-sns-exec.jar \
    && chown fdpuser:fdpuser /local/cmd-adaptor-sns-exec.jar \
    && chmod 0755 /local/opentelemetry-javaagent.jar \
    && chown fdpuser:fdpuser /local/opentelemetry-javaagent.jar

WORKDIR /home/fdpuser
USER fdpuser

CMD ["java", "-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:8077", \
     "-javaagent:/local/opentelemetry-javaagent.jar", \
     "-Dcom.sun.management.jmxremote", "-Dcom.sun.management.jmxremote.port=9012", \
     "-Dcom.sun.management.jmxremote.rmi.port=9012", \
     "-Dcom.sun.management.jmxremote.authenticate=false", \
     "-Dcom.sun.management.jmxremote.local.only=false", \
     "-Dcom.sun.management.jmxremote.ssl=false", \
     "-Djava.rmi.server.hostname=localhost", \
     "-jar", "/local/cmd-adaptor-sns-exec.jar"]
```

This intentionally avoids changing base image, package list, `envconsul` version, healthcheck, entrypoint, debug/JMX defaults, runtime command or Maven build lifecycle.

### 5.6 Measured Results (Customer Machine, Two Independent Runs)

**No-cache builds — measured:**

| Metric | Current Dockerfile | Layer-order prototype | Notes |
|---|---:|---:|---|
| Real time | `87.36s` (run 1), `78.28s` (run 2) | `73.85s` (run 1), `72.64s` (run 2) | The current-vs-prototype gap here is a build-context transfer artefact of running builds back-to-back, **not** a layer-order effect — see below |
| `yum`/`envconsul` step duration | `68.6s` (run 1) | `69.1s` (run 1) | Effectively identical — confirms layer order does not affect cold-build cost, as expected |
| Image size | `875MB` | `875MB` | Unchanged, both runs |
| Smoke check | `current image smoke passed` (java 17.0.19) | `layer-order candidate smoke passed` (java 17.0.19, envconsul v0.13.1) | Both pass, both runs |

Note on the real-time gap in no-cache builds: this comes from `[internal] load build context` transferring `173.48MB` for the current Dockerfile vs `189B` for the prototype in the same run, because the prototype's context was already primed from the immediately preceding build. This is a sequencing artefact of running two builds back-to-back, not a property of either Dockerfile — the actual expensive step (`yum`/`envconsul`) takes the same time in both.

**Warm-cache rebuild after a real JAR content change — measured (this is the actual T3.3 hypothesis):**

First attempt used `touch` (timestamp only) and was inconclusive — both Dockerfiles showed the `COPY` layer as `CACHED` because `touch` does not change content hash. Re-run with a real content change (verified via differing SHA-256 before/after) on two separate occasions:

| Run | Current Dockerfile | Layer-order prototype | `yum`/`envconsul` cached in prototype? | Image size |
|---|---:|---:|:---:|---|
| Run 1 | `77.90s` (yum/envconsul rebuilt, `70.9s`) | `5.08s` | ✅ Yes | `875MB` both |
| Run 2 | `75.82s` (yum/envconsul rebuilt) | `4.62s` | ✅ Yes | `875MB` both |

**Result: confirmed and reproduced.** In the current Dockerfile, `COPY` sits before the `yum`/`envconsul` install, so any JAR change invalidates `COPY` and forces every subsequent layer — including the unrelated `yum`/`envconsul` step — to rebuild (~76–78s). In the layer-order prototype, `COPY` sits after `yum`/`envconsul`, so a JAR change only invalidates `COPY` and the small `chmod`/`chown` step; `yum`/`envconsul` is correctly reused from cache (~4.6–5.1s). The ~15–16x speedup is consistent across both runs and is not a measurement fluke.

## 7. Claims and Non-Claims

Claimed (confirmed by measurement, reproduced across two runs):

- T3.3's local layer-order prototype was built, measured, and produces the same runtime artefacts as the production Dockerfile (smoke check: `java`, `envconsul v0.13.1`, both jars present).
- The production Dockerfile was **not** edited or replaced (SHA-256 confirmed identical before and after every build run: `69d3410e...`).
- Cold-build time and image size are unaffected by layer order (`68.6s` vs `69.1s` for the `yum`/`envconsul` step; `875MB` both images), consistent with the task's own framing that this is not a cold-build optimisation.
- **Same-daemon warm-cache rebuild after a real JAR content change is measurably faster with the layer-order prototype**: `77.90s → 5.08s` (run 1), `75.82s → 4.62s` (run 2), because the expensive `yum`/`envconsul` install is correctly reused from cache instead of rerunning on every JAR-only change.
- Image size is unchanged between current and prototype in every measured build (`875MB`).

Explicitly scoped — what this result does and does not prove:

- This is a **same-daemon, local warm-cache** result from a persistent Docker build cache across consecutive builds. It does **not** by itself prove a CI benefit — Drone/DIND pipeline pods are ephemeral per T1.5's findings, so whether this cache persists between CI pipeline runs (as opposed to between builds on the same daemon within one measurement session) is a separate, unanswered question.
- No CI saving is claimed.
- No image-size reduction is claimed (image size is unchanged, not reduced).
- No production Dockerfile change is made or proposed — the production Dockerfile remains RepoSync-controlled and unmodified.
- No RepoSync/platform recommendation is made — this result should inform, not pre-empt, the Story 6 ownership classification.
- No base-image, package-list, `envconsul`, Maven lifecycle, `CMD`, debug/JMX, healthcheck or runtime-behaviour change is included or claimed.
- No broad adaptor-family rollout is claimed — this was tested on `cmd-adaptor-sns` only.

## 9. Recommendation

**Measured observation: layer-order prototype improves warm-cache rebuild after application JAR change (`~15–16x`, reproduced twice), image size is unchanged, cold build is unaffected, and smoke checks pass.**

Per the recommendation logic below, this maps to: **keep as a candidate for RepoSync/platform ownership discussion (via Story 6), and carry forward into T3.4 for further comparison. Do not adopt into the production Dockerfile yet.**

| Observation | Recommendation | Applies here? |
|-------------|----------------|:---:|
| Layer-order prototype improves warm-cache rebuild after application JAR change, image size remains similar, and smoke checks pass | Keep as a candidate for RepoSync/platform ownership discussion | ✅ **This is the measured outcome** |
| Warm-cache behaviour does not improve materially | Do not proceed with layer-order change; document as measured non-benefit | Not applicable — clear improvement measured |
| Candidate smoke check fails or required artefacts are missing | Stop and fix equivalence before considering the candidate | Not applicable — smoke checks passed both runs |
| Cold build remains similar but warm rebuild improves | Present only as a warm-cache/local same-daemon benefit, not as a cold-build improvement | ✅ **This is exactly the case — see Section 7 scope** |

**Why "carry forward, don't adopt yet":** the measured benefit is real, reproducible, and low-risk (no behavioural change), but it is a same-daemon local result. Drone/DIND pods are ephemeral per T1.5, so whether this warm-cache benefit survives between CI pipeline runs (as opposed to within a single measurement session on one daemon) is untested and out of scope for T3.3. The production Dockerfile remains RepoSync-controlled — any move from prototype to production requires the same ownership-confirmation route already flagged in T3.1/T3.2, independent of this result. This finding should feed into T3.4's before/after comparison and the Story 6 CST-local vs ACP/RepoSync ownership classification, not trigger an immediate production change.
