## 1. Current Dockerfile Shape

The SNS Dockerfile is a packaging Dockerfile. Maven builds the artefacts first, then Docker copies the pre-built JAR and OpenTelemetry agent:

```dockerfile
FROM amazoncorretto:17

COPY ./target/cmd-adaptor-sns-exec.jar /local
COPY ./target/dependencies/opentelemetry-javaagent.jar /local/opentelemetry-javaagent.jar

WORKDIR /tmp

RUN yum install -y shadow-utils unzip \
    && yum update -y ... \
    && curl --silent --output /tmp/envconsul.zip ... \
    && unzip envconsul.zip \
    && adduser -u 1000 -U -m -s /bin/bash fdpuser \
    && chmod/chown copied artefacts

WORKDIR /home/fdpuser
USER fdpuser
CMD ["java", "...", "-javaagent:/local/opentelemetry-javaagent.jar", "-jar", "/local/cmd-adaptor-sns-exec.jar"]
```

This means Story 3 should not assume a Maven multi-stage Dockerfile unless the team deliberately changes the build lifecycle. The initial optimisation should preserve the current "external Maven build -> Docker packaging" model.

## 3. Cache And Repeatability Risks

| Risk | Evidence | Story 3 handling |
|------|----------|------------------|
| Application artefact copied before expensive setup | Current Dockerfile copies the executable JAR before `yum install/update`, envconsul download and user setup | Prototype moving expensive setup before application `COPY`; measure local rebuild impact |
| Monolithic `RUN` | Package install, package update, envconsul download, user creation and artefact permission changes are tied together | Split only where it creates measurable cache or review benefit |
| `yum update` during image build | T1.5 flags repeatability risk | Review with platform/security; prefer approved patched base-image strategy before production change |
| No Docker ignore file | T2.3 found no Docker ignore file and measured `191.27MB` context | Add/propose `.dockerignore` while retaining required runtime artefacts |
| Full-JDK runtime base | `amazoncorretto:17` contributes large lower layers | Review smaller approved runtime base, but do not assume direct public image use |
| Production ownership | T1.5 says production Dockerfile changes require RepoSync route | Treat local Dockerfile changes as prototypes until RepoSync path is confirmed |

Layer reordering is mainly a local rebuild and same-daemon cache improvement. It should not be presented as a guaranteed reduction for a single cold CI build, because Drone/DIND starts with an empty cache and the visible `Command Adaptor` step includes more than Docker build time.

## 4. Build Context Review

The Dockerfile only requires these two artefacts:

```text
target/cmd-adaptor-sns-exec.jar
target/dependencies/opentelemetry-javaagent.jar
```

Everything else in `cmd-adaptor-sns/` should be treated as optional for Docker context unless another Dockerfile instruction requires it.

| Context item | Needed by current Dockerfile? | Action |
|--------------|:-----------------------------:|--------|
| `target/cmd-adaptor-sns-exec.jar` | Yes | Must remain included |
| `target/dependencies/opentelemetry-javaagent.jar` | Yes | Must remain included |
| Other `target/` files | No | Candidate for exclusion |
| `src/` | No | Candidate for exclusion |
| IDE/editor files | No | Exclude |
| VCS metadata/logs/temp files | No | Exclude |

The `.dockerignore` task must not exclude all of `target/` unless the two required runtime artefacts are explicitly re-included and the build is verified.

## 5. Prioritised Opportunities

| Priority | Candidate | Why | Owner / constraint |
|----------|-----------|-----|--------------------|
| 1 | `.dockerignore` retaining only required runtime artefacts | Directly targets measured `191.27MB` context and `target/` dominance | Ownership confirmation pending |
| 2 | Move expensive setup before application `COPY` | Prevents application JAR changes invalidating package/envconsul setup in local/same-daemon cached builds | Production Dockerfile route via RepoSync |
| 3 | Review `yum install/update` layer | Measured `249MB` mutable layer and repeatability concern | RepoSync + security/platform review |
| 4 | Review smaller approved runtime base | Base/rootfs layers are the largest structural driver | Requires approved image-source / Artifactory validation |
| 5 | Split monolithic `RUN` | Improves reviewability and may improve cache granularity | Measure impact; avoid unnecessary layer churn |
| 6 | Review debug/JMX defaults and healthcheck | Security/operability improvement, not a build-time claim by itself | Requires application/runtime validation |

No percentage reduction should be attached to these candidates until T3.4 captures before/after values.
