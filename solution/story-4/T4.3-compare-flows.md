## 5. Target-Machine Measurement Method

Use `docker compose` on the target machine. If the environment only has legacy `docker-compose`, use the equivalent `docker-compose -f "$COMPOSE_FILE" ...` form and record that in the result.

Set the Compose file path:

```bash
COMPOSE_FILE=cmd-adaptor-sns-integration-tests/src/test/resources/docker-compose/docker-compose.yml
```

### Redis-only Compose startup-to-ready run

Run this twice, recording Run 1 and Run 2 separately.

```bash
RUN_LABEL=compose-run-1
KEY="t43-compose-redis-${RUN_LABEL}"
VALUE="value-${RUN_LABEL}"

docker compose -f "$COMPOSE_FILE" down --remove-orphans

START=$(date +%s%N)
docker compose -f "$COMPOSE_FILE" up -d redis

until [ "$(docker compose -f "$COMPOSE_FILE" exec -T redis redis-cli ping 2>/dev/null)" = "PONG" ]; do
  sleep 0.2
done
END=$(date +%s%N)

awk "BEGIN {print \"compose_startup_to_ready_seconds=\" (($END-$START)/1000000000)}"

docker compose -f "$COMPOSE_FILE" exec -T redis redis-cli ping
docker compose -f "$COMPOSE_FILE" exec -T redis redis-cli set "$KEY" "$VALUE"
docker compose -f "$COMPOSE_FILE" exec -T redis redis-cli get "$KEY"
docker compose -f "$COMPOSE_FILE" exec -T redis redis-cli del "$KEY"

CLEANUP_START=$(date +%s%N)
docker compose -f "$COMPOSE_FILE" down --remove-orphans
CLEANUP_END=$(date +%s%N)

awk "BEGIN {print \"compose_cleanup_seconds=\" (($CLEANUP_END-$CLEANUP_START)/1000000000)}"
```

For Run 2, change `RUN_LABEL=compose-run-2`.

Record for each run:

- exact command form used: `docker compose` or `docker-compose`
- Docker version and Compose version
- image state: cold image pull, image already local, or unknown
- startup-to-ready time from `up -d redis` through successful `redis-cli ping`
- `PING` result
- `SET`/`GET` result and key cleanup result
- cleanup time
- whether the second run used a different key and did not depend on state from Run 1

### Optional mapped-port smoke check

The Compose `redis-cli` checks prove Redis is ready inside the Compose service. To match the T4.2 Testcontainers mapped-port evidence more closely, also run a host-to-container check against `localhost:6379` if a local Redis client is available:

```bash
redis-cli -h localhost -p 6379 ping
redis-cli -h localhost -p 6379 set t43-compose-host-check value
redis-cli -h localhost -p 6379 get t43-compose-host-check
redis-cli -h localhost -p 6379 del t43-compose-host-check
```

If no host Redis client is available, document that the Compose check used `redis-cli` inside the running Redis container. That is still useful support-flow evidence, but it is weaker than Java/Jedis mapped-port evidence because it does not prove host-to-container connectivity from the test JVM.

### Optional full E2E Compose timing

Full E2E timing may be captured only as contextual evidence:

```bash
/usr/bin/time -p mvn \
  -pl cmd-adaptor-sns-integration-tests \
  -am \
  -Plocal-int-cmd \
  verify
```

Do not compare this directly with the Redis-only Testcontainers smoke test. The full E2E flow includes Kafka, Schema Registry, Kafdrop, topic creation, aggregators, application startup and Cucumber execution.

## 7. Benefits, Drawbacks and Limitations

Benefits observed for Testcontainers Option A:

- Runs as a local, opt-in Redis-only smoke/wiring test.
- Uses Java/Jedis to prove mapped host/port connectivity from the test JVM.
- Preserves existing docker-compose E2E flow and CI/default profile semantics.
- Provides isolated Redis state with fresh container lifecycle and UUID keys.

Docker Compose Redis structural benefits:

- Uses the same `redis:5.0.6` image/tag as the existing integration-test environment.
- Already exists in the RepoSync-controlled compose file.
- Exposes fixed `localhost:6379`, which can be convenient for manual checks when no port conflict exists.

Docker Compose Redis observed benefits:

- Redis-only service was successfully started and exercised independently.
- Functional validation passed twice.
- Unique run-specific values were used.
- Explicit cleanup completed successfully and consistently.

Limitations:

- Startup-to-ready timing was not captured.
- Compose checks used `redis-cli` inside the Compose service.
- Java/Jedis host-to-container connectivity was not independently tested for Compose.
- Fixed host port `6379` may conflict locally.
- Broader Compose file warnings were emitted for `CORE_TAG`, `DOCKER_USER` and obsolete `version`.
- The existing `redis_kafka` pre-integration readiness path is not Redis-only and must not be used as a Redis startup timer.
- Full E2E Compose timing is contextual only and not comparable to a Redis-only Testcontainers smoke test.
- No CI measurement has been performed.

## 9. Recommendation

Both Redis-only paths were functionally valid within their different scopes. Testcontainers proves Java/Jedis mapped-port wiring with automatic container lifecycle management. Docker Compose proves that the existing Redis support service can be started and exercised independently, with successful repeated functional checks and explicit cleanup.

Because Compose startup-to-ready timing was not captured, no performance preference is established. Do not proceed to Redis Option B on performance grounds from the current evidence.

A rerun is required only if startup-to-ready timing is still considered necessary for the decision. If rerun, capture:

- `compose_startup_to_ready_seconds` for Run 1 and Run 2
- Docker/Compose version
- image state

Final recommendation within current evidence:

1. Treat Option A as functionally validated for Redis Testcontainers wiring.
2. Keep Maven elapsed time, test-framework time, startup-to-ready time and cleanup time separate.
3. Do not make a performance preference between Testcontainers and Compose without Compose startup-to-ready timing.
4. Do not recommend CI adoption from local-only results.
5. Consider Kafka and Schema Registry follow-up on coverage/isolation value, not on unmeasured Redis performance grounds.
