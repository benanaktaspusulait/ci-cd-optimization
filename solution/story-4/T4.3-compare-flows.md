## B. Structural Observations (from repository review)

The following are structural observations derived from reviewing the repository configuration. They are not measurement results and must not be treated as such.

### B1. Scope difference

- The T4.2 Testcontainers test starts **only** a Redis container.
- The existing full E2E docker-compose flow (activated by `local-int-cmd` or `local-int-snapshot`) starts Redis **plus** Kafka, Schema Registry, LocalStack, Jaeger, Kafdrop, 6 aggregators, and the command adaptor.
- These two flows have **different coverage** and must not be compared as equivalent runtimes.

### B2. Compose readiness dependency

- The existing docker-compose readiness check `redis_kafka` (in `pre-integration-test/app.py`) combines Redis readiness with Kafka, Schema Registry, and Kafdrop readiness, plus Kafka topic creation.
- Therefore, any timing measured against the `redis_kafka` readiness stage **cannot** be treated as Redis-only startup timing.

### B3. Compose Redis service

- The docker-compose file defines a `redis` service using `redis:5.0.6` with a health check: `["CMD", "redis-cli", "ping"]`.
- Whether the Redis service can be started independently (without other compose services) depends on compose dependency configuration. This has **not been validated**.
- `docker-compose up -d redis` may or may not be safe without the full compose context. Repository validation is required before attempting Redis-only compose measurement.
