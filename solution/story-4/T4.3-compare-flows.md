## 1. Side-by-Side Comparison

| Dimension | Docker Compose (current) | Testcontainers (proposed) |
|-----------|-------------------------|--------------------------|
| **Startup time** | ~2-4 min (full stack) | ~5-20s (per test class, subset only) |
| **Services started** | 17+ (all, regardless of test needs) | 1-3 (only what the test needs) |
| **State isolation** | None — shared Kafka topics, Redis, schemas | Full — fresh containers per test class |
| **Port management** | Fixed (6379, 9092, 8081...) | Random (dynamic port mapping) |
| **Cleanup** | `docker-compose down` (manual or post-integration-test phase) | Automatic (Ryuk or JVM shutdown) |
| **Parallel execution** | Impossible (port conflicts) | Possible (random ports) |
| **Flakiness risk** | High (shared state, ordering deps) | Low (isolated, deterministic) |
| **Developer experience** | Slow feedback (~4 min to first test) | Fast feedback (~20s to first test) |
| **CI requirement** | DIND + compose steps in pipeline | DIND + `DOCKER_HOST` env var on Maven step |
| **Configuration** | `docker-compose.yml` + `.env` + profiles | Java code (type-safe, version-controlled) |
| **Dependency management** | Image tags in YAML | Image tags in Java constants |
| **Network** | Docker bridge network | Testcontainers managed network |
| **Debugging** | `docker-compose logs`, Kafdrop UI | Container logs in test output, Testcontainers log consumers |

## 2. Startup Time Comparison

### Docker Compose (full stack for any integration test)

```
ZooKeeper                    ~5-10s
Kafka (after ZK)             ~10-20s
Schema Registry (after Kafka) ~10-15s
Redis                        ~2-3s
LocalStack                   ~10-20s
Jaeger                       ~5s
Kafdrop                      ~10s
6x Aggregators               ~30-60s each (parallel but JVM warmup)
Command Adaptor              ~15-30s (docker build + start)
Wait checks (sequential)     ~30-60s
─────────────────────────────────────
TOTAL                        ~2-4 minutes
```

### Testcontainers (Redis-only test)

```
Redis container              ~2-3s
─────────────────────────────────────
TOTAL                        ~3 seconds
```

### Testcontainers (Kafka + Schema Registry test)

```
Kafka (KRaft mode, no ZK)   ~10-15s
Schema Registry              ~5-10s
─────────────────────────────────────
TOTAL                        ~15-25 seconds
```

**Improvement:** From ~2-4 minutes → ~3-25 seconds (**85-98% reduction** in test startup time).

## 3. Test Isolation Comparison

### Docker Compose: Shared State Problems

```
Test A writes "key1" to Redis
Test B reads "key1" from Redis — PASSES (depends on Test A running first!)
Test B runs alone — FAILS (key1 doesn't exist)

Test C produces message to topic-X
Test D consumes from topic-X — gets Test C's message (unexpected!)
```

### Testcontainers: Isolated State

```
Test A: gets fresh Redis → writes "key1" → asserts → container destroyed
Test B: gets fresh Redis → empty → test logic stands alone → PASSES

Test C: gets fresh Kafka → produces → consumes → asserts → container destroyed
Test D: gets fresh Kafka → only sees its own messages → PASSES
```

## 4. Developer Workflow Comparison

### With Docker Compose (today)

```bash
# Developer wants to run one integration test:
cd cmd-adaptor-sns-integration-tests

# Option 1: Full stack (slow)
mvn verify -Plocal-int-snapshot     # 4-6 minutes before first test runs

# Option 2: Partial (still needs manual compose up first)
docker-compose -f src/test/resources/docker-compose/docker-compose.yml up -d
# Wait for services... check logs... retry if something fails...
mvn verify -Plocal-int-cmd          # 2-3 minutes
docker-compose -f src/test/resources/docker-compose/docker-compose.yml down
```

### With Testcontainers (proposed)

```bash
# Developer wants to run one integration test:
mvn verify -Ptestcontainers         # 20-30 seconds, everything handled automatically

# Or run a specific test class:
mvn test -Ptestcontainers -Dtest=RedisCacheTcIntegrationTest   # ~5 seconds
```

## 5. When to Use Each Approach

| Scenario | Recommended Approach |
|----------|---------------------|
| Testing Redis cache logic in isolation | **Testcontainers** |
| Testing Kafka message flow in isolation | **Testcontainers** |
| Testing full end-to-end flow (adaptor → aggregators → output) | **Docker Compose** (aggregators are custom apps) |
| Testing adaptor startup and health | **Testcontainers** (just infra deps) |
| Local debugging with Kafdrop/Jaeger UI | **Docker Compose** (UI tools included) |
| CI pipeline integration tests | **Docker Compose** (today) → **Testcontainers** (future, with RepoSync change) |
| Quick developer feedback | **Testcontainers** |

## 6. Migration Strategy

### Phase 1: Coexistence (current recommendation)

```
Existing Cucumber tests          → Docker Compose (unchanged)
New isolated unit-integration    → Testcontainers
```

Both approaches coexist. No existing tests are modified.

### Phase 2: Progressive Migration

```
Tests that only need Redis       → Convert to Testcontainers
Tests that only need Kafka       → Convert to Testcontainers
Tests that need full stack       → Keep on Docker Compose
```

### Phase 3: Compose Reduction (Story 5)

```
CI compose services              → Only aggregators + command adaptor
Infrastructure (Kafka, Redis)    → Testcontainers (started by Maven)
```

## 7. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Team unfamiliarity with Testcontainers | Medium | Provide examples + pairing session |
| Docker Desktop licensing on developer machines | Low | Testcontainers works with Colima, Rancher Desktop, Podman |
| Container image pull time on first run | Low | Images cached after first pull; same images as compose |
| Test execution time increases (container per class) | Low | Testcontainers reuse mode for local dev; still faster than full compose |
| Aggregators can't easily be Testcontainers-ified | N/A | Keep aggregators in compose; Testcontainers for infra only |
