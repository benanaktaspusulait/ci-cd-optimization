## 1. Final Outcome

The Redis-first Option A pilot achieved its local functional smoke/wiring goal. Two local runs showed that `MinimalRedisTest` could start `redis:5.0.6`, connect from the Java test JVM through the Testcontainers-mapped host and port, and pass `PING` and UUID-based `SET`/`GET` checks.

The existing Docker Compose Redis service also passed two Redis-only functional runs using `redis-cli` inside the container. These checks establish that both paths worked within their different scopes. They do not establish a performance preference because Compose startup-to-ready timing was not captured.

```text
Option A = functionally complete for the local Redis smoke/wiring scope
Option B = not a current follow-up candidate from Story 4 evidence
Kafka and Schema Registry = follow-up candidates for a separately scoped coverage/isolation objective, not validated outcomes
CI adoption = not evaluated by this pilot
```

Measurement boundaries:

- The results are local Redis-only smoke/wiring evidence, not full E2E timings.
- The measured test used a non-static `@Container`, giving each test method a fresh Redis container, and unique UUID key/value data.

## 3. Observed Findings

| Finding | Evidence-supported interpretation |
|---|---|
| Option A functional goal | Achieved locally: `MinimalRedisTest` passed twice using Java/Jedis through the Testcontainers-mapped host and port. |
| Repeated Testcontainers execution | The measured smoke test used a fresh container lifecycle and unique UUID key/value data. This is limited to the measured Redis test and is not a claim about system-wide isolation. |
| Compose Redis-only functional path | Worked twice for `PING`, `SET`, `GET` and `DEL`, followed by explicit cleanup. |
| Connectivity scope differs | Testcontainers proved connectivity from the Java test JVM. Compose was checked with `redis-cli` inside the Compose service, so host-to-container Java/Jedis equivalence was not demonstrated. |
| Performance comparison | No conclusion is available because Compose startup-to-ready timing was not captured and Testcontainers container startup was not measured separately. |
| Existing flow impact | The Option A pilot was opt-in through `local-testcontainers`; existing Compose, CI and default profile behaviour was not changed by T4.2. |

Repository/configuration observations remain separate from runtime findings. Repository review identified the Compose Redis service as `redis:5.0.6`, with host port `6379:6379`, a `redis-cli ping` healthcheck, no observed Redis service-level `depends_on`, no Redis service volume requirement and the default Compose network. These are configuration observations, not additional runtime measurements.

## 6. Recommendation

1. **Close Option A as functionally complete for its narrow local goal.** The implementation and two successful runs are sufficient evidence for Redis Testcontainers smoke/wiring.
2. **Do not treat Option B as a current follow-up candidate.** Story 4 provides no performance justification for it. Reconsider Option B only if a separate non-performance objective is agreed, such as validating a local-profile Redis override.
3. **Treat Kafka and Schema Registry as follow-up candidates when the next objective is coverage or isolation in the Kafka-driven integration path.** This priority comes from [T4.1 candidate/scope evidence](./T4.1-select-candidate.md), based on the earlier [T2.4 integration-test baseline](../story-2/T2.4-integration-test-baseline.md); it is not inferred from Redis performance.
4. **Make CI a separate validation step only if adoption is proposed.** Run and measure the pilot on the target platform before deciding any `DOCKER_HOST`, Ryuk, image-source or pipeline configuration.
5. **Preserve the existing Compose E2E path.** The Redis pilot did not demonstrate full Compose replacement.

RepoSync governance boundary:

```text
Temporary target-repository experimentation may be used for the pilot.
No durable RepoSync-managed adoption or broad rollout was approved.
```

### Continue/stop decision

- Continue using the completed Option A implementation as local, opt-in Redis smoke/wiring evidence.
- Stop further Redis performance conclusions until comparable measurements exist.
- Do not start Option B without a separately agreed non-performance objective.
- Treat Kafka/Schema Registry as follow-up candidates for a separately scoped coverage/isolation objective.
- Consider CI follow-up only as separately scoped and validated work.
