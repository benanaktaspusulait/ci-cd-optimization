## 3. Confirmed Candidate Scope

| Candidate | T4.1 decision | Reason |
|---|---|---|
| Redis | Confirmed as Phase 1 | Single support dependency; small enough to validate Testcontainers startup, dependency wiring, connectivity, isolation and local workflow. |
| Kafka + Schema Registry | Follow-up | Higher value for the real integration-test path, but higher setup complexity and stronger topic/message/offset isolation concerns. |
| Full docker-compose replacement | Out of scope | Too broad for Phase 1 and requires separate follow-up design and measurement. |

Phase 1 scope:

- Add a local, opt-in Redis Testcontainers smoke/wiring test.
- Start a Redis container with Testcontainers.
- Connect to Redis through the mapped host/port.
- Perform a simple `PING` and `SET/GET` interaction.
- Verify repeated local execution does not depend on state left by a previous run.
- Keep the current docker-compose E2E flow unchanged.

## 4. Implementation-Readiness Record

| Item | Selected T4.2 route | Evidence / guardrail |
|---|---|---|
| Target module | `cmd-adaptor-sns-integration-tests` | The root POM includes the integration-test module. |
| Test framework | Isolated JUnit Jupiter smoke test in the existing integration-test module | `junit-jupiter` is already present; the smoke test should not be added to the existing Cucumber E2E path. |
| Test class shape | Add a focused class such as `MinimalRedisTest` under `src/test/java` | Keeps the pilot small and separately runnable. |
| Testcontainers dependency route | Add Testcontainers through repo-local Maven dependency management/version property, with test-scoped dependencies in the integration-test module | No Testcontainers dependency is currently present. T4.2 should record the exact resolved version and source route. |
| Redis client route | Add a minimal test-scoped Java Redis client dependency for the smoke test | No Java Redis client dependency was found in the checked POMs. A mapped-port client test gives stronger evidence than only running `redis-cli` inside the container. |
| Redis interaction | `PING` plus `SET/GET` against `redis.getHost()` and `redis.getMappedPort(6379)` | Confirms Redis is reachable from the test JVM, not only alive inside the container. |
| Redis image/tag | `redis:5.0.6` | Matches the docker-compose baseline. |
| Redis image-source route | Use the locally validated or approved image source for `redis:5.0.6`; do not assume direct public-registry access for CI | T1.4 keeps public-registry and CI image-source validation as follow-up work. |
| Opt-in execution | Use a local opt-in Maven route such as `local-testcontainers` plus an isolated test include or `-Dtest=MinimalRedisTest` | Do not change `local-int-cmd`, `local-int-snapshot`, `ci-cmd` or `ci-snapshot` semantics. |
| State isolation | Use a unique test key and cleanup/reset state before or after the assertion | Repeated local executions must not depend on previous Redis state. |
| Existing compose flow | Leave docker-compose, `WAIT_CHECK=redis_kafka` and full Cucumber E2E flow unchanged | Current compose/pre-integration files are RepoSync-controlled and are not Redis-only measurement paths. |

Dependency note:

T4.2 should avoid adding Kafka, Schema Registry, LocalStack or broad Testcontainers modules during the Redis pilot. If dependency policy blocks a new Java Redis client, the fallback is to use the Redis image's `redis-cli` through Testcontainers and record that as weaker connectivity evidence because it does not prove mapped-port access from the test JVM.
