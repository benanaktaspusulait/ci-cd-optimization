## 5. Key Architectural Decisions

> Source: architecture review (Story 1 synthesis). These are the cross-cutting decisions the pilot must agree; each maps to an ownership item above. **The "Recommendation" column records a recommended option, not a locked decision** — the structural choices (especially a/f–j) must be ratified through the sequence in T1.2 "Decision Order".

| # | Decision question | Recommendation | Owner / route |
|---|-------------------|----------------|---------------|
| a | Should compose be owned by Drone or **Maven**? | **Recommended option: Maven** (decision required). Make `mvn verify` the single orchestration entry point; Drone provisions DIND and calls it. `pom.xml` is repo-local → team-owned; gives local/CI parity and removes the 6-vs-7 aggregator / dual-`CORE_TAG` divergence. **Alternative: Drone retains ownership.** See T1.2 "Decision 1 — Options". (B10) | CST design + RepoSync MR for `DOCKER_HOST` |
| b | Should the duplicate Maven build be removed? | **Yes — via build-once-promote.** Build the image once, test/scan that artifact, publish the same digest. Closes the release-integrity gap, not just wasted time. (B9) | RepoSync MR (CI + Artifactory) |
| c | Should Trivy fail the pipeline? | **Yes, staged.** Triage current findings, then fail on CRITICAL with an expiring `.trivyignore` waiver. Do not flip `--exit-code 1` before triage. | ACP/security + RepoSync |
| d | Should Sonar run on feature branches? | **Yes for analysis, with a caveat.** Pre-merge value is real, but the pipeline notes HO Sonar ingests a single branch — full per-branch gating may need a Sonar branch-analysis/licensing change. Conditional on Sonar config. | ACP / Sonar admin |
| e | Should the `pull_request` pipeline be removed? | **Remove or repurpose.** It validates nothing and branch-push CI already gives feedback. Keep only a minimal status-check pipeline if GitLab requires a required check on the MR; otherwise delete. | RepoSync MR |

**Sequencing note:** (a) and (b) are the highest-value structural decisions and unlock the rest; (c)/(d)/(e) are governance/cleanup decisions that can proceed in parallel once stakeholders agree thresholds. The full structural dependency order is in **T1.2 "Decision Order"**: lifecycle ownership → orchestration model → compose role → build lifecycle → optimisation. Making optimisation decisions before ownership is settled causes rework.

### 5.1 Structural Ownership Decisions (from T1.2 System-Level Architecture)

These deeper structural decisions sit beneath (a). They define the target ownership model and cannot be answered by file inspection — they require an owner to choose. Source: T1.2 "Required Architectural Decisions".

| # | Decision question | Recommendation | Owner / route |
|---|-------------------|----------------|---------------|
| f | Should `docker-compose.yml` be split into an **infra definition** (platform) and a **test contract** (test)? | **Lean yes.** The file currently conflates two concerns with two audiences; splitting lets test authors change the test contract without a platform MR. Confirm feasibility within RepoSync templating. | CST proposal → RepoSync/ACP |
| g | Should Testcontainers **replace** the infra tier or **coexist**? | **Replace the infra tier over time** (one model), starting coexistence in the pilot. Avoid a permanent three-model state (Drone compose + Maven compose + Testcontainers). | CST design (S4/S5) |
| h | Is docker-compose a **platform concern** or a **test concern**? | **Infra tier = platform; topology/wait contract = test.** This determines whether the infra tier should remain RepoSync-owned at all. | ACP + CST |
| i | Should the `skip.*` control plane be **eliminated**? | **Yes — converge on one orchestration path** identical locally and in CI, removing the repo-local lever over central behaviour. | CST design + RepoSync MR |
| j | **Where should the test contract live** so test authors can change it without a central MR? | Move service/port/wait expectations into **repo-local test code / Testcontainers**, leaving only platform infra centrally owned. | CST design (S4/S5) |

**Relationship to (a):** decision (a) picks the orchestrator (Maven); (f)–(j) define what that orchestrator owns and what stays central. They should be decided together as the "target ownership model," then executed via the T5.3 §8 migration plan.
