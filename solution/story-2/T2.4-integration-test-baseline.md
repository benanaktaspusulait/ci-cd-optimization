## 1. How Integration Tests Are Currently Started

The working pilot baseline remains `fdp-cmd-adaptor-sns`. `fdp-cmd-adaptor-dvla` has been checked from the provided source excerpts as the lightweight comparison candidate to validate that the same integration-test orchestration pattern exists beyond SNS.

### In CI (Drone Pipeline)

The integration tests run inside a Docker Compose container, orchestrated by the CI pipeline:

```text
Pipeline Step 10: "Integration Tests"
├── Wait for command adaptor ready (compose up pre-integration-test, WAIT_CHECK=command_adaptor)
├── Wait for aggregators ready (compose up pre-integration-test, WAIT_CHECK=aggregators)
├── docker-compose ps (debug listing)
├── docker-compose up --exit-code-from integration-tests integration-tests
└── bin/integration-test.sh (local hook)
```

The `integration-tests` service definition:
```yaml
integration-tests:
  container_name: integration-tests
  entrypoint: mvn -Pci-snapshot install
  image: quay.io/ukhomeofficedigital/ileap-java17-mvn:1.3
  volumes:
    - "../../../../..:/app"
  working_dir: /app
```

**Key insight:** The test container mounts the entire repo and runs `mvn -Pci-snapshot install` — this is a **full Maven build inside the container**, not just test execution.

### Locally (Developer Machine)

Developers use Maven profiles with the docker-compose-maven-plugin:

```bash
# Full local integration (all services + aggregators)
mvn install -Plocal-int-snapshot

# Partial (command adaptor only, no aggregators)
mvn install -Plocal-int-cmd
```

The `docker-compose-maven-plugin` in `cmd-adaptor-sns-integration-tests/pom.xml` orchestrates:
1. Start infrastructure (Kafka, Redis, ZK, Schema Registry, LocalStack, Jaeger, Kafdrop)
2. Start aggregators (6 services)
3. Wait for aggregators ready
4. Start command adaptor
5. Wait for command adaptor ready
6. **Run integration tests** (Cucumber via failsafe plugin)
7. Tear down all compose services

## 4. Test Execution Detail

### Test Framework

| Property | Value |
|----------|-------|
| Framework | Cucumber (BDD) |
| Runner | JUnit 5 with vintage engine (JUnit 4 compatibility) |
| Test discovery | `**/*IntegrationTest` pattern (failsafe plugin) |
| Maven profile | `ci-snapshot` (in CI), `local-int-snapshot` or `local-int-cmd` (locally) |

### ci-snapshot Profile Behaviour

```xml
<profile>
    <id>ci-snapshot</id>
    <properties>
        <skip.containers>true</skip.containers>      <!-- Don't start compose from Maven -->
        <skip.aggregators>true</skip.aggregators>    <!-- Don't start aggregators from Maven -->
        <skip.integration.tests>false</skip.integration.tests>  <!-- DO run tests -->
        <kafka.bootstrap.server.host>kafka</kafka.bootstrap.server.host>
        <kafka.bootstrap.server.port>29092</kafka.bootstrap.server.port>
        <kafka.schemaregistry.server.host>schema-registry</kafka.schemaregistry.server.host>
        <kafka.schemaregistry.server.port>8081</kafka.schemaregistry.server.port>
    </properties>
</profile>
```

**Key:** `skip.containers=true` means the Maven docker-compose-plugin is skipped in CI — infrastructure is already running via the pipeline compose steps. The tests just connect to `kafka:29092` and `schema-registry:8081` (Docker network hostnames).

### Integration Test Container Mounts

```yaml
volumes:
  - "../../../../..:/app"    # Entire repo mounted into container
working_dir: /app
entrypoint: mvn -Pci-snapshot install
```

This means the integration-tests container runs a **full Maven install** (compile + test all modules) — not just integration tests. This confirms the duplicate build suspicion from T1.3.

## 5. Known Pain Points

### 5.1 Full Stack Required for Any Integration Test

Even a simple test that only touches Redis needs:
- Zookeeper + Kafka + Schema Registry (because aggregators depend on them)
- All 6 aggregators (because test infrastructure starts everything)
- Command Adaptor (because it's the system under test)
- LocalStack (IAM mock)

**Impact:** Can't run a quick, isolated integration test without the full stack (~17 containers).

### 5.2 Long Startup Time

~60-120s just for infrastructure, then ~30-60s for aggregators, then wait checks. Total time from "I want to run a test" to "test starts executing": **~2-4 minutes**.

### 5.3 Shared State Between Tests

All tests share the same Kafka topics, Redis instance, and aggregator state. If test A writes to a topic and test B reads from it, ordering matters. This creates:
- Hidden dependencies between tests
- Flaky failures when test order changes
- Difficulty running tests in parallel

### 5.4 Duplicate Maven Build in CI

The CI pipeline runs `mvn clean install` in step 7 (builds everything), then the `integration-tests` container runs `mvn -Pci-snapshot install` again (builds everything + runs integration tests). The compile/package phase is duplicated.

DVLA shows the same duplicate-build shape: a pipeline-level `mvn clean install` plus an `integration-tests` compose service that runs `mvn -Pci-snapshot install`.

### 5.5 Non-Deterministic Environment

- `yum update` in Dockerfile pulls latest packages (different on different days)
- `localstack:0.12.18` is pinned but very old (current is 3.x) — may have unfixed bugs
- `redis:5.0.6` is pinned but EOL
- Aggregator images use `${CORE_TAG}` variable — version changes can break tests

### 5.6 No Test Isolation

Tests run within a single JVM, against shared infrastructure. A test that doesn't clean up properly (e.g., leaves messages on a Kafka topic) can cause the next test to fail or produce false positives.

**Testcontainers would solve:** 5.1 (subset of deps), 5.2 (faster startup for subset), 5.3 (fresh state per test class), 5.6 (isolated containers per test).

## 7. Testcontainers Opportunity (Preview for Story 4)

Based on this baseline, the best Testcontainers candidates are:

| Dependency | Difficulty | Isolation Benefit | Startup Speed |
|-----------|:----------:|:-----------------:|:-------------:|
| **Redis** | Easy | High (no shared cache state) | ~2-3s |
| **Kafka + Schema Registry** | Medium | High (no shared topics) | ~15-20s |
| **LocalStack** | Easy | Medium (IAM mock) | ~10-15s |
| Aggregators | Hard (custom apps) | Low (need real images) | ~30s each |

**Recommended first candidate:** Redis — simplest, fastest startup, highest isolation benefit.
