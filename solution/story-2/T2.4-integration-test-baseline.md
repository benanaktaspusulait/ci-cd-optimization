## 1. How Integration Tests Are Currently Started

The working pilot baseline remains `fdp-cmd-adaptor-sns`. `fdp-cmd-adaptor-dvla` has been checked from the provided source excerpts as the lightweight comparison candidate to validate that the same integration-test orchestration pattern exists beyond SNS.

### In CI (Drone Pipeline)

The integration tests run inside a Docker Compose container, orchestrated by the CI pipeline:

```text
Pipeline Step 10: "Integration Tests"
├── Wait for command adaptor ready (compose up pre-integration-test, WAIT_CHECK=command_adaptor)
├── Wait for aggregators ready (compose up pre-integration-test, WAIT_CHECK=aggregators)
├── docker-compose ps (debug listing)
├── docker-compose up --exit-code-from integration-tests integration-tests
└── bin/integration-test.sh (local hook)
```

The `integration-tests` service definition:
```yaml
integration-tests:
  container_name: integration-tests
  entrypoint: mvn -Pci-snapshot install
  image: quay.io/ukhomeofficedigital/ileap-java17-mvn:1.3
  volumes:
    - "../../../../..:/app"
  working_dir: /app
```

**Key insight:** The test container mounts the entire repo and runs `mvn -Pci-snapshot install` — this is a **full Maven build inside the container**, not just test execution.

### Locally (Developer Machine)

Developers use Maven profiles with the docker-compose-maven-plugin:

```bash
# Full local integration (all services + aggregators)
mvn install -Plocal-int-snapshot

# Partial (command adaptor only, no aggregators)
mvn install -Plocal-int-cmd
```

The `docker-compose-maven-plugin` in `cmd-adaptor-sns-integration-tests/pom.xml` orchestrates:
1. Start infrastructure (Kafka, Redis, ZK, Schema Registry, LocalStack, Jaeger, Kafdrop)
2. Start aggregators (6 services)
3. Wait for aggregators ready
4. Start command adaptor
5. Wait for command adaptor ready
6. **Run integration tests** (Cucumber via failsafe plugin)
7. Tear down all compose services

## 5. Structural Pain Points and Risks

### 5.1 Full Stack Required for Any Integration Test

**Current structural observation:** the CI/local integration-test shape starts the full infrastructure, aggregator family, command adaptor and supporting mock services before integration tests run.

Even a simple test that only touches Redis needs:
- Zookeeper + Kafka + Schema Registry (because aggregators depend on them)
- All 6 aggregators (because test infrastructure starts everything)
- Command Adaptor (because it's the system under test)
- LocalStack (IAM mock)

**Risk:** developers and CI cannot run a quick, isolated integration test without the full stack (~17 containers).

**Evidence still needed:** review SNS integration-test classes to identify which tests can run with a reduced dependency set.

### 5.2 Long Startup Time

**Current structural observation:** the pipeline starts infrastructure first, then aggregators, then command adaptor, with wait checks before integration tests run.

**Risk:** startup overhead may dominate integration-test elapsed time. Estimated at ~60-120s just for infrastructure, then ~30-60s for aggregators, then wait checks. Total estimated time from "I want to run a test" to "test starts executing": **~2-4 minutes**.

**Current evidence:** Build #881 provides one successful log sample showing Integration Tests outer step `09:40`, Maven total `08:27 min` and `cmd-adaptor-sns-integration-testing` reactor module `07:52 min`.

**Evidence still needed:** additional successful step logs only if an N=10 internal wait/build/test split is required.

### 5.3 Shared State Between Tests

**Current structural observation:** tests use shared Kafka, Redis and aggregator-backed infrastructure.

**Risk:** shared state may create order dependency or false positives if tests do not clean up data correctly. This can create:
- Hidden dependencies between tests
- Potential flaky failures when test order changes
- Difficulty running tests in parallel

**Evidence still needed:** observed failures, rerun history, or test-class review. Do not classify a failure as flaky unless either repeated rerun success or team evidence supports it.

The T2.2 failed/unsuccessful sample gives reliability context but does not yet prove that shared state or lack of isolation caused flaky tests.

### 5.4 Duplicate Maven Build in CI

**Current structural observation:** the CI pipeline runs a pipeline-level `mvn clean install` (builds everything), then the `integration-tests` container runs `mvn -Pci-snapshot install` again (builds everything + runs integration tests).

**Risk:** the compile/package phase appears duplicated. This is a strong candidate for optimisation analysis, but no saving is claimed until an implementation change is tested before/after.

**Current evidence:** the pipeline-level Maven build average from T2.2 is `01:24`; Build #881 shows integration-test container Maven total `08:27` and `cmd-adaptor-sns-integration-testing` module duration `07:52`.

| Build activity | Current evidence | Measurement status |
|----------------|------------------|--------------------|
| Pipeline-level Maven build | T2.2 N=10 average `01:24` | Measured outer CI step |
| Integration-test container Maven run | Build #881 Maven total `08:27` | Measured one successful log sample |
| Integration-test module execution | Build #881 `cmd-adaptor-sns-integration-testing` `07:52` | Measured one successful log sample |
| Duplicated compile/package cost | Structurally likely | Needs Maven phase-level confirmation before claiming savings |

This strengthens the optimisation case, but no saving is claimed until an implementation change is tested before/after.

DVLA shows the same duplicate-build shape: a pipeline-level `mvn clean install` plus an `integration-tests` compose service that runs `mvn -Pci-snapshot install`.

### 5.5 Non-Deterministic Environment

- `yum update` in Dockerfile pulls latest packages (different on different days)
- `localstack:0.12.18` is pinned but very old (current is 3.x) — may have unfixed bugs
- `redis:5.0.6` is pinned but EOL
- Aggregator images use `${CORE_TAG}` variable — version changes can break tests

### 5.6 No Test Isolation

**Current structural observation:** tests run within a single JVM, against shared infrastructure.

**Risk:** a test that does not clean up properly (e.g., leaves messages on a Kafka topic) can cause the next test to fail or produce false positives.

**Evidence still needed:** test-class review, observed failures, rerun history, or team confirmation.

The T2.2 failed/unsuccessful sample gives reliability context but does not yet prove that shared state or lack of isolation caused flaky tests.

**Testcontainers could reduce or improve:** 5.1 (subset of dependencies), 5.2 (faster startup for selected dependencies), 5.3 (fresh state per test class), and 5.6 (more isolated containers per test or test class). Aggregators and the full application stack would still need migration design.
