---

## 1. Purpose

This document defines the Redis Testcontainers pilot scope, implementation approach, risks and measurement plan. Redis is selected as a low-complexity first pilot to validate Testcontainers wiring and workflow.

This pilot is not intended to solve the main Kafka topic/message/offset isolation path. T2.4 found that Kafka + Schema Registry are the central integration-test input/assertion path and remain the higher-value follow-up candidate.

---

## 2. Decision Summary

Decision:

`Use Redis as the first Testcontainers pilot.`

Rationale:

- Lower implementation complexity than Kafka + Schema Registry.
- Suitable for one-engineer pilot.
- Validates Testcontainers dependency wiring pattern.
- Allows limited-scope learning without redesigning Kafka, Schema Registry, aggregators or command-adaptor orchestration.

Non-goals:

- Do not claim to solve Kafka topic/message/offset isolation.
- Do not claim CI time saving before measurement.
- Do not replace the full docker-compose integration-test stack.
- Do not edit centrally controlled `pre-integration-test/app.py` locally unless the upstream RepoSync source is changed.
- Do not claim flaky tests are fixed.

---

## 3. Current Redis Usage

The reviewed `pre-integration-test/app.py` is centrally controlled and contains the warning `DO NOT EDIT LOCALLY`. It also states that local changes in the command-adaptor repository will be overwritten by RepoSync. The Redis pilot should therefore avoid directly editing this file unless the change is made in the central source/repo-sync owner path.

Observed Redis behaviour in `pre-integration-test/app.py`:

- `WAIT_CHECK` determines the startup stage.
- Startup stage `1` maps to `redis_kafka`.
- When `WAIT_CHECK == "redis_kafka"`, the script creates a Redis client using `redis.Redis("redis")`.
- The script waits until `rs.ping()` succeeds.
- The same stage then waits for Schema Registry, waits for Kafdrop, sorts Kafka topics and creates them via `create_kafka_topics("kafka:29092", topic_names)`.

| Area | Current behaviour | Pilot implication |
|------|-------------------|-------------------|
| `pre-integration-test/app.py` | Uses `redis.Redis("redis")` during `WAIT_CHECK=redis_kafka` and waits for `ping()` | Redis hostname is hard-coded in startup utility |
| `redis_kafka` stage | Waits for Redis, Schema Registry, Kafdrop, then creates Kafka topics | Redis pilot cannot blindly replace the whole stage |
| Docker Compose | Provides Redis service and network hostname `redis` | Testcontainers pilot must decide whether to replace, override, or run alongside compose Redis |
| Java test path | No direct Redis assertion path observed in `SnsSteps.java` | Redis pilot is infrastructure/support scope, not central assertion scope |

The reviewed `README.md` describes a Maven multi-module project with `cmd-adaptor-sns-common`, `cmd-adaptor-sns` and `cmd-adaptor-sns-integration-tests`. The integration-test module is a full containerised docker-compose build with BDD Cucumber feature-file driven E2E tests.

Existing integration-test workflow:

- `local-int-cmd` starts containers, but not the Aker aggregators.
- `local-int-snapshot` starts containers, including the Aker aggregators.
- `mvn -Plocal-int-cmd clean install` runs the command-adaptor local integration path.
- `mvn -Plocal-int-snapshot clean install` runs the snapshot local integration path.
- `mvn integration-test -Plocal-int-snapshot` leaves containers up and reduces the build-test cycle.
- `mvn clean integration-test -Plocal-int-snapshot` restarts containers and clears Kafka topics.

The Redis pilot must fit this existing Maven/profile/docker-compose developer workflow and should avoid disrupting the documented local integration-test path.

## 4. Pilot Scope Options

### Option A — Minimal learning pilot

Description:

Add a small Testcontainers-based Redis smoke/integration test that validates Redis container startup and configuration wiring without changing the full existing E2E flow.

Pros:

- Lowest risk.
- Does not disturb current docker-compose E2E tests.
- Good first proof of Testcontainers in this repo.

Cons:

- Does not replace the compose Redis service.
- Limited value for CI timing.
- Does not prove full E2E compatibility.

Conclusion:

Recommended first step if team availability is very limited.

### Option B — Local profile Redis override pilot

Description:

Introduce a dedicated Maven/profile or test configuration path that starts Redis via Testcontainers and points the relevant runtime config to the Testcontainers Redis host/port for selected local testing.

Pros:

- More meaningful than a smoke test.
- Still smaller than Kafka + Schema Registry.
- Can validate wiring pattern.

Cons:

- Existing `pre-integration-test/app.py` hard-codes `redis.Redis("redis")`.
- May require configuration or compose override design.
- Must avoid editing central RepoSync-controlled script locally.

Conclusion:

Recommended target for the actual Redis pilot plan after Option A is proven.

### Option C — Replace compose Redis in full E2E flow

Description:

Remove or bypass compose Redis and use Testcontainers Redis in the current full integration-test flow.

Pros:

- Highest Redis-specific value.

Cons:

- Riskier.
- Docker network/hostname compatibility issue likely.
- `pre-integration-test/app.py` expects hostname `redis`.
- Full E2E flow still depends on Kafka, Schema Registry, aggregators and command adaptor.
- Could require broader orchestration redesign.

Conclusion:

Not recommended as the first implementation step.

---

## 5. Recommended Pilot Route

Recommended route:

`Option A first, then Option B if successful.`

Given this pilot is likely to be progressed by one engineer and the current startup utility is centrally controlled, the safest route is:

1. Add a minimal Redis Testcontainers smoke/wiring test.
2. Use the result to validate dependencies, Maven setup and local developer workflow.
3. Then design a local/profile-based Redis override if the smoke pilot is accepted.
4. Keep full E2E docker-compose flow unchanged initially.

This route validates Testcontainers with a small implementation surface while avoiding claims that Redis is the main integration-test assertion path.

---

## 6. Proposed Technical Approach

### Phase 1 — Add Testcontainers dependency

Add the Testcontainers Redis dependency in the integration-test module only.

Do not provide or introduce an exact Testcontainers version unless it is already defined in dependency management. If dependency management already exists, use the existing managed version.

### Phase 2 — Add minimal Redis container test

Create a small test class, for example:

`RedisTestcontainersPilotTest`

Purpose:

- Start Redis container.
- Connect with Redis client.
- Set/get simple key.
- Confirm container lifecycle works under Maven profile.

This test should be separate from the existing Cucumber E2E path. It should not require feature files, Kafka, Schema Registry, aggregators or command-adaptor startup.

### Phase 3 — Validate Maven/profile integration

Decide whether the pilot runs:

- during normal integration test profile
- under a dedicated profile
- or as a separate pilot-only test

Recommended:

Use a dedicated profile or naming pattern to avoid disrupting existing E2E flow.

The first useful command should be local and narrow. The pilot should not require the full docker-compose E2E stack to prove the Testcontainers Redis lifecycle.

### Phase 4 — Optional profile-based Redis wiring

Only after Phase 1-3 succeed, investigate whether the runtime Redis endpoint can be externalised enough to point at Testcontainers Redis.

This phase should answer:

- Where Redis host/port configuration is supplied to the integration-test/runtime path.
- Whether the existing `redis` hostname assumption can be avoided or replaced in a controlled way.
- Whether a docker network alias is needed.
- Whether the change belongs in the command-adaptor repo or the central RepoSync-managed source.
- Whether the local Maven/profile workflow can remain compatible with the README commands.

Do not attempt to replace the whole `redis_kafka` startup stage in the first pilot.

## 7. Risks and Constraints

| Risk | Why it matters | Mitigation |
|------|----------------|------------|
| `app.py` is centrally controlled | Local edits may be overwritten by RepoSync | Avoid local edits or change the central source |
| Redis hostname is hard-coded as `redis` | Testcontainers exposes dynamic host/port by default | Start with smoke test; later evaluate network alias or config override |
| `redis_kafka` stage combines Redis + Kafka readiness | Redis is not isolated in the startup utility | Do not replace the whole stage in first pilot |
| Full E2E still depends on Kafka/Schema Registry | Redis pilot will not validate central assertion path | Explicitly keep Kafka + Schema Registry as follow-up |
| CI timing improvement may be small | Redis is not the dominant observed test cost | Do not claim savings until measured |
| Existing developer workflow relies on docker-compose profiles | Breaking local workflow would reduce adoption | Keep existing profiles unchanged in first step |

## 8. Measurement Plan

Before implementation:

- Record current local command duration if available.
- Record current CI Integration Tests step duration from T2.4/T2.2 baseline.
- Record developer workflow impact qualitatively.

After Phase 1:

- Confirm Testcontainers Redis starts reliably.
- Confirm test passes locally.
- Confirm dependency does not break existing E2E build.
- Record added test execution time.

After Phase 2/3:

- Record whether the pilot can run independently.
- Record whether existing docker-compose E2E path remains unchanged.
- Record any CI impact if wired into CI.

Do not claim:

- CI saving
- flaky-test reduction
- Kafka isolation improvement

until measured.
