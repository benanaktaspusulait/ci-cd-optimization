## 1. Current Dockerfile And Image-Shape Analysis

The working pilot baseline remains `fdp-cmd-adaptor-sns`. `fdp-cmd-adaptor-dvla` has been checked as the lightweight comparison candidate from the provided source excerpts to confirm whether the Dockerfile and build-image findings are portable across the FDP adaptor family.

### Base Image

| Property | Value |
|----------|-------|
| Base image | `amazoncorretto:17` |
| Type | Full JDK (not JRE) |
| Visible base/rootfs contribution | 165MB + 300MB in Docker history |
| OS | Amazon Linux based / tag-dependent |
| Package manager | yum |

The use of `amazoncorretto:17` is the main structural image-size driver because it is a full JDK runtime image. The application Dockerfile packages a pre-built JAR and does not require a compiler toolchain at runtime.

### Current Build Approach

The Dockerfile does **not** build the application — it only packages a pre-built JAR:

```dockerfile
FROM amazoncorretto:17

COPY ./target/cmd-adaptor-sns-exec.jar /local
COPY ./target/dependencies/opentelemetry-javaagent.jar /local/opentelemetry-javaagent.jar

RUN yum install -y shadow-utils unzip \
    && yum update -y [many packages] \
    && yum erase -y vim-data \
    && yum clean all \
    && curl ... envconsul ... \
    && adduser fdpuser \
    && chmod/chown ...

USER fdpuser
CMD ["java", "-javaagent:...", "-jar", "/local/cmd-adaptor-sns-exec.jar"]
```

**Flow:** Maven builds the JAR externally in the CI Maven build step → Dockerfile copies JAR + OTel agent → installs system deps → creates user → runs.

This means image-size and build-time optimisation should focus on runtime image selection, package installation behaviour, Docker build context size, and repeatability of the package/update layer rather than on moving Java compilation into the Dockerfile.

## 2. Current Build Context

### Build Context Path

The Docker build context is `cmd-adaptor-sns/`:
- **In CI (compose build):** docker-compose.yml points the command-adaptor build to the cmd-adaptor-sns context (relative path observed as `../../../../../cmd-adaptor-sns`).
- **In Artifactory pipeline:** `.drone.star` explicitly sets `'context': 'cmd-adaptor-sns'` and `'dockerfile': 'cmd-adaptor-sns/Dockerfile'`.

### Docker Ignore Status

**SNS repository:** The local validation found no Docker ignore file using `find . -iname '*dockerignore*' -print`.

This means the entire `cmd-adaptor-sns/` directory can be sent as build context, including:
- `target/` (build output — only the exec JAR and OTel agent are needed)
- `src/` (Java source code — not needed, but not the main context-size driver)
- `pom.xml` (not needed in build)
- Any IDE files, logs, etc.

**DVLA comparison:** No Docker ignore evidence was present in the provided DVLA excerpts. That should be treated as unconfirmed rather than confirmed absent.

### Build Context Baseline

| Metric | Value | Method |
|--------|-------|--------|
| Docker ignore file | Not found | `find . -iname '*dockerignore*' -print` |
| Local module directory size after artefact preparation | 356M | `du -sh cmd-adaptor-sns/` |
| Local target directory size | 353M | `du -sh cmd-adaptor-sns/target/` |
| Local source directory size | 2.4M | `du -sh cmd-adaptor-sns/src/` |
| Full Docker build context transferred | 191.27MB | Docker build output from full build |
| Warm/cached build context shown | 189B | Docker build output from cached run |

| Path | Measured size | Interpretation |
|------|---------------|----------------|
| `cmd-adaptor-sns/` | 356M | Local module directory after artefact preparation |
| `cmd-adaptor-sns/target/` | 353M | Dominant contributor to local module size |
| `cmd-adaptor-sns/src/` | 2.4M | Source code is not the main context-size driver |

The full Docker build transferred 191.27MB of context once the required target artefacts were present. Local directory-size checks show that `target/` is the dominant contributor to the module size after artefact preparation. The warm cached run later showed a much smaller context value because the build was cached.

After artefact preparation, the local module directory size is dominated by `target/`. The Dockerfile only needs `cmd-adaptor-sns-exec.jar` and `target/dependencies/opentelemetry-javaagent.jar`, but the broader `target/` directory can be included in the build context when no effective Docker ignore file is present. Therefore, the context-reduction opportunity is mainly about excluding unnecessary generated artefacts while explicitly keeping the two required runtime artefacts.

The previous `~110-170 MB` context estimate has been superseded by the measured `191.27MB` full build context transfer.

## 5. Image-Size Baseline

A local Docker image was successfully produced after the required Maven artefacts were present. The measured final image size is 906MB.

| Metric | Measured Value | Notes |
|--------|----------------|-------|
| Final image size | 906MB | `docker images cmd-adaptor-sns:baseline` |
| Executable JAR copied into image | 173MB in Docker history / 166M local file size | Main application artefact |
| OpenTelemetry Java agent | 18MB | Copied into `/local` |
| `yum install/update` layer | 249MB | Largest Dockerfile-created mutable layer |
| Base/runtime layers visible in history | 165MB + 300MB | Base image contribution visible from Docker history |

The previous `~530-610 MB` directional estimate is superseded by the measured `906MB` image-size baseline.

### Why the Image is Large

1. **Full JDK/base layers** — `amazoncorretto:17` contributes visible 165MB and 300MB lower layers in Docker history.
2. **Large executable JAR** — the application artefact is 166M locally and appears as a 173MB Docker layer.
3. **yum install/update layer** — measured at 249MB.
4. **OpenTelemetry agent** — adds 18MB.
5. **envconsul/runtime tooling** — included in the RUN layer.
6. **No multi-stage or smaller runtime image** — the image currently packages everything into a full JDK runtime image.

## 6. Optimisation Potential (Preview)

| Change | Expected Directional Impact | Evidence | Likely Change Route / Confirmation Needed |
|--------|-----------------------------|----------|-------------------------------------------|
| Reduce or replace full JDK base image | Large image-size reduction potential | Base/runtime layers visible in history | RepoSync-level change; runtime compatibility needs confirmation |
| Review `yum install/update` layer | High potential; measured layer is 249MB | Docker history | RepoSync/security policy confirmation |
| Add effective Docker ignore file | Build context reduction potential by excluding unnecessary generated artefacts while retaining the executable JAR and OpenTelemetry agent | No Docker ignore file found; target directory is 353M; Dockerfile only requires two target artefacts | Confirm RepoSync/local ownership |
| Review executable JAR contents | Potential reduction only if artefact composition can be changed | JAR copied layer 173MB | Application packaging review |
| Review envconsul/runtime tooling | Potential reduction if no longer required | Included in RUN layer | Runtime usage confirmation |

These are candidate optimisation areas, not approved implementation changes. Exact savings should not be claimed until before/after measurements exist. Because the Dockerfile appears RepoSync-controlled, most durable changes are expected to require a RepoSync-level change rather than a local adaptor-only change.

DVLA strengthens the portability case for the base-image and `yum update` recommendations because its app Dockerfile uses the same RepoSync-controlled `amazoncorretto:17` runtime pattern. The Docker ignore recommendation remains confirmed for SNS and should be checked directly in DVLA before being claimed there.
