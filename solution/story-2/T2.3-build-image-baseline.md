## 1. Current Dockerfile And Image-Shape Analysis

The working pilot baseline remains `fdp-cmd-adaptor-sns`. `fdp-cmd-adaptor-dvla` has been checked as the lightweight comparison candidate from the provided source excerpts to confirm whether the Dockerfile and build-image findings are portable across the FDP adaptor family.

### Base Image

| Property | Value |
|----------|-------|
| Base image | `amazoncorretto:17` |
| Type | Full JDK (not JRE) |
| Estimated size | ~450-480 MB |
| OS | Amazon Linux 2 |
| Package manager | yum |

The use of `amazoncorretto:17` is the main structural image-size driver because it is a full JDK runtime image. The application Dockerfile packages a pre-built JAR and does not require a compiler toolchain at runtime.

### Current Build Approach

The Dockerfile does **not** build the application — it only packages a pre-built JAR:

```dockerfile
FROM amazoncorretto:17

COPY ./target/cmd-adaptor-sns-exec.jar /local
COPY ./target/dependencies/opentelemetry-javaagent.jar /local/opentelemetry-javaagent.jar

RUN yum install -y shadow-utils unzip \
    && yum update -y [many packages] \
    && yum erase -y vim-data \
    && yum clean all \
    && curl ... envconsul ... \
    && adduser fdpuser \
    && chmod/chown ...

USER fdpuser
CMD ["java", "-javaagent:...", "-jar", "/local/cmd-adaptor-sns-exec.jar"]
```

**Flow:** Maven builds the JAR externally (CI step 7) → Dockerfile copies JAR + OTel agent → installs system deps → creates user → runs.

This means image-size and build-time optimisation should focus on runtime image selection, package installation behaviour, Docker build context size, and repeatability of the package/update layer rather than on moving Java compilation into the Dockerfile.

## 2. Current Build Context

### Build Context Path

The Docker build context is `cmd-adaptor-sns/`:
- **In CI (compose build):** docker-compose.yml specifies `build: ../../../../../cmd-adaptor-sns` for the `command-adaptor` service.
- **In Artifactory pipeline:** `.drone.star` explicitly sets `'context': 'cmd-adaptor-sns'` and `'dockerfile': 'cmd-adaptor-sns/Dockerfile'`.

### .dockerignore Status

**SNS repository:** Does not exist. There is no `.dockerignore` file anywhere in the analysed SNS repository.

This means the entire `cmd-adaptor-sns/` directory is sent as build context, including:
- `src/` (all Java source code — not needed, JAR is pre-built)
- `target/` (build output — only the exec JAR and OTel agent are needed)
- `pom.xml` (not needed in build)
- Any IDE files, logs, etc.

**DVLA comparison:** No `.dockerignore` evidence was present in the provided DVLA excerpts. That should be treated as unconfirmed rather than confirmed absent.

### Build Context Size Estimate

| Directory | Estimated Size | Needed in Docker build? |
|-----------|----------------|:-----------------------:|
| `target/` (full) | ~100-150 MB | Only 2 files (~50-80 MB) |
| `src/` | ~5-10 MB | No |
| `pom.xml` | <1 KB | No |
| Other files | ~1-5 MB | No |
| **Total context sent** | **~110-170 MB** | |
| **Actually needed** | **~50-80 MB** | (2 JAR files only) |

Potential unnecessary context: ~60-90 MB per build, subject to actual repository size confirmation.

The key baseline finding is structural: the Dockerfile only needs the executable JAR and OpenTelemetry agent, but without a `.dockerignore` the broader adaptor directory can be sent as build context.

## 5. Image-Size Baseline Estimate

No actual image-size measurement was captured in this task because the local validation attempt failed before producing an image. The estimated range is based on the full JDK base image, copied application artefacts, OpenTelemetry agent and package/update layer. Actual values should be measured with `docker images` and `docker history` after the required target artefacts exist if a strict numerical baseline is required.

| Metric | Estimated Value | Target (pilot) |
|--------|-----------------|----------------|
| Final image size | ~530-610 MB | Candidate for reduction review |
| Base image size | ~450-480 MB | Candidate for JRE/smaller runtime review |
| Application layer | ~50-80 MB | Review only if artefact composition changes |
| System deps layer | ~30-50 MB | Candidate for package/update review |

### Why the Image is Large

1. **Full JDK** — `amazoncorretto:17` includes compiler and development tooling not needed at runtime.
2. **yum update** — pulls updated packages into a new layer.
3. **Amazon Linux 2** — heavier than Alpine/distroless alternatives.
4. **envconsul binary** — 15MB+ added for Vault integration.
5. **No multi-stage** — everything is packaged in one image.

## 6. Optimisation Potential (Preview)

| Change | Expected Directional Impact | Effort | Owner / Change Route |
|--------|-----------------------------|--------|----------------------|
| Switch to `amazoncorretto:17-alpine` or `eclipse-temurin:17-jre-alpine` | Large image-size reduction expected; exact saving requires before/after image measurement | Low | RepoSync MR |
| Add `.dockerignore` | Build context reduction expected; exact saving requires build-context measurement | Low | RepoSync MR (or local if not synced) |
| Remove `yum update` (pin base image version) | Improves repeatability and may reduce build time/layer churn | Low | RepoSync MR |
| Multi-stage | Cleaner separation if build concerns are moved or artefact preparation changes | Medium | RepoSync MR |
| Remove envconsul | Potential small reduction only if runtime usage is confirmed unnecessary | Low | Investigate usage |

These are candidate optimisation areas, not approved implementation changes. Because the Dockerfile appears RepoSync-controlled, most durable changes are expected to require a RepoSync-level change rather than a local adaptor-only change.

DVLA strengthens the portability case for the base-image and `yum update` recommendations because its app Dockerfile uses the same RepoSync-controlled `amazoncorretto:17` runtime pattern. The `.dockerignore` recommendation remains confirmed for SNS and should be checked directly in DVLA before being claimed there.
