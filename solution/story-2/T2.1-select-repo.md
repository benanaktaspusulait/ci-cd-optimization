## 1. Candidate Assessment

### Selected Repository: `fdp-cmd-adaptor-sns`

This is the repository we are currently working in. Based on Story 1 findings, this repo is already well-understood and is the current working recommendation for the pilot target.

### Selection Rationale

| Criterion | fdp-cmd-adaptor-sns | Notes |
|-----------|:-------------------:|-------|
| Pipeline complexity | High | Full CI pipeline: Maven build + 6 aggregators + Kafka + Redis + LocalStack + integration tests |
| Docker Compose usage | Heavy | 20 services defined in docker-compose.yml (17 started in CI) |
| Integration test complexity | High | Cucumber-based, multiple wait cycles, full stack required |
| RepoSync-managed | Yes | Standard FDP adaptor — patterns are likely reusable to others |
| Current delivery priority/risk | Low | SNS adaptor is stable — safe to experiment on |
| Portability | High | FDP adaptors appear to use the same RepoSync pipeline family/template |
| Java version | 17 | Testcontainers compatible |
| Build tool | Maven (multi-module) | Standard for all FDP repos |

### Candidate Comparison

`fdp-cmd-adaptor-dvla` is used as the lightweight second candidate. The purpose is not to run a full Story 1 assessment on DVLA, but to confirm whether the SNS findings are portable across the FDP adaptor pipeline family.

| Criterion | fdp-cmd-adaptor-sns | fdp-cmd-adaptor-dvla | Notes |
|-----------|:-------------------:|:--------------------:|-------|
| Same RepoSync template family | Yes | Expected / needs quick confirmation | Confirms portability if DVLA uses the same RepoSync pipeline family/template |
| Pipeline complexity | High | Expected medium-high | Both are FDP command adaptors; exact DVLA pipeline shape should be checked briefly |
| Docker Compose usage | Heavy | Expected similar / TBC | Confirm whether DVLA uses the same compose orchestration pattern |
| Integration-test complexity | High | TBC | Check integration-test module, Maven profiles and compose dependencies |
| Dockerfile ownership | RepoSync-controlled | Expected RepoSync-controlled / TBC | Confirm from Dockerfile header or RepoSync source |
| Testcontainers suitability | High | Expected similar / TBC | Likely similar if Maven/Testcontainers/DIND constraints match SNS |
| Build optimisation potential | High | Expected similar / TBC | Likely similar if Dockerfile/base-image/build-context are template-driven |
| Delivery risk | Low | TBC | Needs stakeholder input before using DVLA as pilot target |
| Access/source available | Yes | TBC | Pilot needs practical source and CI access |
| Suitability for pilot | High | Comparison only | SNS remains selected because it is already analysed, understood and lower-risk |

### Why This Repo (and not another)

1. **Representative** — appears to use the same RepoSync pipeline family/template as other FDP adaptors
2. **Accessible** — we have the source code and can run builds locally
3. **Low risk** — SNS feed is stable; changes won't disrupt active delivery
4. **Complex enough** — has the full integration test stack (Kafka, Redis, Schema Registry, LocalStack, 6+ aggregators)
5. **Portable patterns** — improvements here can be evaluated for transfer to other adaptors via RepoSync

### Portability Notes

| What transfers to other adaptors | What is SNS-specific |
|----------------------------------|---------------------|
| Dockerfile optimisations (adaptors appear to use the same template family) | AVRO schema specifics (`sns-ens`) |
| `.dockerignore` (same build structure) | Feed-specific test data |
| Testcontainers setup (same infra deps) | `LOCALSTACK_SERVICES=iam` |
| Maven profile approach | `KAFKA_TOPIC_SUFFIX=sns` |
| Compose service mapping (same services) | Adaptor-specific business logic |
| Pipeline observations (same `.drone.star`) | — |

## 3. Maven Profiles (Integration Tests)

| Profile | Use case | Skips containers? | Skips tests? |
|---------|----------|:-----------------:|:------------:|
| `local` (default) | Normal dev — no tests | Yes | Yes |
| `local-int-cmd` | Local integration (cmd only, no aggregators) | No | No |
| `local-int-snapshot` | Local integration (full stack) | No | No |
| `ci-cmd` | 6point6 GitHub Workflow | Yes (external) | No |
| `ci-snapshot` | **HO ACP GitLab/Drone** — used in CI pipeline | Yes (external) | No |
| `k8s-dacc-dde-dev` | K8s dev namespace | Yes (external) | No |
| `k8s-dacc-dde-test` | K8s test namespace | Yes (external) | No |
| `k8s-dacc-fdp-dev` | K8s FDP dev namespace | Yes (external) | No |

The `ci-snapshot` profile is what the CI pipeline's `integration-tests` docker-compose container uses. It sets `skip.containers=true` because the compose orchestration handles infra externally.
