## Executive Summary

This assessment separates changes that can be made directly in the adaptor repository from changes that must go through RepoSync or ACP/platform ownership:

- Repo-local Maven/test changes can start now.
- CI, Dockerfile, Compose, BuildKit, cache and DIND-related changes are centrally controlled or platform-dependent.
- Testcontainers CI is **config-feasible** (env-var precedent exists), but adoption is gated on a **container-lifecycle ownership decision**, not on configuration — see System-Level Architecture below.
- This document is not ACP sign-off.

This analysis does not request central changes yet. It defines safe local work, identifies centrally controlled files, and lists the ACP/RepoSync confirmations required before CI/runtime-impacting changes are proposed.

Immediate work should focus on repo-local Maven/test changes and local hook experiments. Any CI, Dockerfile, Compose, BuildKit, cache, DIND, or platform-runtime change should be handled through RepoSync/ACP with a pilot and rollback plan.

The open ACP/RepoSync items are follow-up confirmations for future central changes. They are not blockers for closing this boundary analysis task.

## Main Answer

### Decision Rule

Before changing a file, classify it as:

1. **Repo-local** - safe to change in the adaptor repo.
2. **RepoSync-controlled** - change must go through the RepoSync source repository.
3. **Platform/ACP-owned** - change requires ACP/platform coordination or ticket.
4. **Unknown** - do not rely on it for CI savings until ownership is confirmed.

If a file has a RepoSync warning header, do not edit it locally except for throwaway experiments.

## System-Level Architecture (Cross-Boundary)

> The classifications above answer *"who may edit this file."* They do **not** answer *"who owns this behaviour at runtime."* The following gaps are system-level and are not resolved by file ownership. Architectural and orchestration decisions are addressed by [T5.2 — Section 7: Architectural and Ownership Candidates](../story-5/T5.2-decide-compose-role.md#7-architectural-and-ownership-candidates); runtime mapping by **T1.4 §7** and **T1.3**.

### Architectural Gaps

- **Container lifecycle has no single owner.** Start/stop is owned by Drone in CI and by Maven locally, selected at runtime by **repo-local** `skip.containers` / `skip.aggregators` in `pom.xml`. A repo-local file therefore steers the runtime behaviour of a RepoSync-owned resource — a dependency the ownership tables cannot express.
- **The `skip.*` flags are an unnamed cross-boundary control plane.** They are the actual switch between "Drone owns lifecycle" and "Maven owns lifecycle." Repo-local config silently reassigns central responsibility.
- **`docker-compose.yml` is both an infra definition and a test contract.** One RepoSync-owned file carries a platform concern (image versions, networking, DIND) and a test concern (which services/ports/waits a test needs). Test-driven changes are forced through platform change control.
- **Local and CI are different runtimes despite shared files.** Maven path starts 7 aggregators; Drone path starts 6; `CORE_TAG` resolves two ways. "Validated locally" ≠ "validated as CI runs it."
- **Repo-local artefacts have central blast radius.** Local hooks and test code execute inside RepoSync-owned DIND steps and can fail CI — repo-local edit scope, central runtime impact.
- **"Editable locally" ≠ "effective in production."** The boundary that governs CI outcomes is the *effect* boundary (central), not the *edit* boundary (local).

### Responsibility Model Clarification

| Layer | Concern | Current owner | Ambiguity |
|-------|---------|---------------|-----------|
| CI orchestration | Provision DIND, sequence steps, gate merge | Drone (`.drone.star`, RepoSync) | Clear |
| Test orchestration | Bring up dependencies, readiness, teardown | **Drone in CI / Maven locally** | **Unowned across environments** |
| Container lifecycle | Actual start/stop of services | Whichever orchestrator is active (`skip.*`-selected) | **No single owner** |
| Infra definition | Image versions, networking, topology | `docker-compose.yml` (RepoSync) | Mixed with test contract |
| Test contract | Which services/ports/waits a test needs | Test code (repo-local) + compose (central) | **Split across the boundary** |

> Until test orchestration and container lifecycle have a single named owner across both environments, every later optimisation (Testcontainers, compose reduction, build-once) is negotiating an undefined boundary.

### System Coupling Risks

| Direction | Risk |
|-----------|------|
| Repo-local → central | A test needing a new dependency requires a RepoSync compose change; the repo-local change is not self-contained. |
| Central → repo-local (hidden) | A RepoSync topology change (service rename, port, version) can break repo-local tests/hooks with no signal in the repo. |
| Control-plane | Repo-local `skip.*` flags change which central mechanism runs. |
| Resolution-path | `CORE_TAG` derived independently on each side → repo-local property and central extraction can disagree. |
| Hook | Repo-local hook failure propagates into the central pipeline result. |

### Required Architectural Decisions

These are **decisions**, not confirmations — they require an owner to choose, not a file to inspect. They are presented as options; none are pre-locked here. (Decision register: **T6.2 §5**.)

1. **Who owns container lifecycle across all environments — Drone or Maven?** *(Decision required — see options below.)*
2. **Should `docker-compose.yml` be split into an infra definition (platform) and a test contract (test)?**
3. **Should Testcontainers replace the infra tier, or coexist?** (Replace = one model; coexist = a third model — see Testcontainers Positioning below.)
4. **Is docker-compose a platform concern or a test concern?** (Decides whether the infra tier should stay RepoSync-owned at all.)
5. **Should the `skip.*` control plane be eliminated** in favour of one orchestration path identical locally and in CI?
6. **Where does the test contract live** so test authors can change it without a central MR?
7. **Who owns the build lifecycle and the "final artifact"?** (CI builds and tests one image; the ECR/Artifactory pipeline builds another to publish — see Build Lifecycle Ownership below.)

#### Decision 1 — Options (no pre-locked choice)

| | Option A — Maven owns lifecycle | Option B — Drone owns lifecycle |
|--|--------------------------------|--------------------------------|
| Mechanism | `mvn verify` brings up dependencies; Drone provisions DIND and calls Maven | `.drone.star` steps bring up dependencies; Maven only runs tests |
| Pros | Repo-local control (`pom.xml`); local == CI by construction; removes `skip.*` dual path | Keeps orchestration in the platform layer; no Maven Docker access needed |
| Cons | Requires `DOCKER_HOST` on CI Maven step (RepoSync MR); more responsibility in the build | Local and CI stay different runtimes; `skip.*` divergence persists; logic stays RepoSync-owned (team cannot change it) |
| Status | **Decision required** | **Decision required** |

### Build Lifecycle Ownership

The container/test orchestration is not the only unowned lifecycle — the **build lifecycle** is split too:

- The CI pipeline builds the command-adaptor image (compose `--build`), integration-tests it, and Trivy-scans it.
- The ECR/Artifactory pipeline then performs a **separate** `docker build` and pushes that image.
- So **the tested/scanned image and the published image are different builds**, and there is **no single owner of the "final artifact."**

**Open decision (not a confirmed gap):** is the second build intentional (clean separation of test vs publish) or an unmanaged duplication? Either way, the *artifact identity* must be owned. Options: (A) **build-once-promote** — build once, test/scan, publish the same digest; (B) **keep two builds** but pin inputs so they are provably equivalent. **Decision required.** (Cross-ref: Story 3 SUMMARY, T6.2 §5b / B9.)

---

### Testcontainers Positioning (Realistic)

Introducing Testcontainers does **not** by itself simplify the system. There are already two orchestration mechanisms (Drone compose, Maven compose plugin); adding Testcontainers without retiring one creates a **third orchestration model**.

- **Coexistence** is a valid *transitional* state, not an end state. Held long-term it increases the maintenance and divergence surface (now three places encode topology/readiness).
- **Migration implication:** each Testcontainers adoption step should **retire** the corresponding compose responsibility (e.g. infra tier moves to TC → infra services leave compose), so the model count goes 2 → (transient 3) → 1, not 2 → 3 permanently.
- Therefore Testcontainers is **config-feasible** but its value is conditional on Decisions 1, 3 and 5 being made first; otherwise it adds surface rather than removing it.

---

### Target End State

A decision-ready target the options above should converge on (the *what*, not the *who* — ownership is Decision 1):

1. **One orchestration model** exercised identically locally and in CI (no `skip.*` fork).
2. **One named container-lifecycle owner** (the chosen orchestrator), with the build lifecycle owning a single, promoted artifact.
3. **Infrastructure definition separated from the test contract** — platform owns infra (images, networking); test authors own service/port/wait expectations in repo-local code.
4. **Infra tier** provided by isolated, per-run containers (Testcontainers or equivalent); **custom-app tier** (aggregators, command-adaptor) remains explicitly defined and centrally governed.
5. **Local and CI execution paths aligned** so "passes locally" means "passes as CI runs it."

---

### Decision Order (Sequence Matters)

The decisions are **dependent**, so order is not arbitrary. Optimisations made before ownership is settled will be reworked.

1. **Container lifecycle ownership** (Decision 1) — everything else assumes a single owner.
2. **Orchestration model** (Decisions 3, 5) — Drone compose / Maven compose / Testcontainers; only meaningful once the owner is fixed.
3. **docker-compose role** (Decisions 2, 4) — infra definition vs test contract; depends on the chosen model.
4. **Build lifecycle ownership** (Decision 7) — artifact identity / build-once-promote; depends on which stage owns the tested image.
5. **Optimisation** (BuildKit, cache, compose reduction) — last, because each optimisation’s shape depends on all of the above.

**Why order matters:** e.g. reducing compose services (step 5) before settling the orchestration model (step 2) means re-doing the reduction once Testcontainers ownership changes what compose is even responsible for; enabling BuildKit cache before build-lifecycle ownership (step 4) optimises a build that may be eliminated by build-once-promote.

### System Direction Risks (If We Do Nothing)

| Gap | If unaddressed | Why it is unstable long-term |
|-----|----------------|------------------------------|
| Dual orchestration ownership | Drone and Maven encodings keep diverging (already 6 vs 7 aggregators, dual `CORE_TAG`) | Local and CI silently test different systems; "works locally / fails in CI" becomes structural, not incidental |
| Container lifecycle has no owner | `skip.*` remains the de-facto control plane | A repo-local flag keeps steering central runtime behaviour; no one can reason about or safely change lifecycle |
| compose = infra + test contract | Every test-driven change needs a platform MR | Test iteration is throttled by platform change control; the file accretes conflicting concerns |
| Build lifecycle split | Tested image ≠ shipped image | Green CI and Trivy results apply to a discarded artifact — a latent release-integrity/supply-chain exposure |
| Testcontainers added without retiring a layer | Three orchestration models persist | Maintenance and divergence surface grows; the intended simplification produces the opposite |

> These are **direction risks**, not current outages. The system runs today; the point is that each gap compounds with change and makes the next change more expensive.

| `bin/pre-integration-test-local.sh` | `bin/pre-integration-test.sh` | Pre-Integration Tests | DIND image; `DOCKER_HOST=tcp://docker:2375`; `ADAPTOR_NAME=sns` | Expected to fail the step if the hook exits non-zero without error suppression; confirm with one hook smoke test |
| `bin/integration-test-local.sh` | `bin/integration-test.sh` | Integration Tests | DIND image; `ADAPTOR_NAME=sns`; `DOCKER_HOST` not explicitly set in `.drone.star` | Expected to fail the step if the hook exits non-zero without error suppression; confirm with one hook smoke test |

Operational cautions:

- Hooks are safe extension points, but they are not isolated from CI; if committed, they run in the shared pipeline.
- Hooks should be idempotent and fast.
- Hooks that rely on Docker should explicitly verify Docker access at start.
- Hooks should log enough context to debug failures without dumping secrets.
- Hooks should not assume local developer paths or macOS-specific Docker socket locations.

### Appendix G — Compose Reduction Boundary

Reducing Compose services cannot be treated as a simple local cleanup because `docker-compose.yml` is RepoSync-controlled and many services are shared infrastructure for the E2E path.

Before proposing service removal, produce a dependency graph:

| Service group | Examples | Needed evidence before removal |
|---------------|----------|--------------------------------|
| Core infra | Kafka, Zookeeper, Schema Registry, Redis, LocalStack | Which tests/topics/commands require each service |
| Observability/debug | Kafdrop, Jaeger | Whether CI assertions depend on them or they are debug-only |
| Aggregators | event/location/object/party/service/matching | Which adaptor output path or pre-integration step depends on each |
| Wait/helper containers | `pre-integration-test`, `wait4localstack` | Whether wait logic can move into script/Testcontainers safely |
| Application under test | `command-adaptor`, integration-tests | Must remain unless test architecture changes |

Any Compose reduction should be piloted with a single adaptor and a rollback-ready RepoSync MR.

### Appendix I — Blast Radius, Rollout and Rollback

RepoSync changes may affect multiple adaptor repositories, not just SNS. Treat central changes as platform changes unless ACP confirms a pilot-only path.

| Change type | Potential blast radius | Pilot strategy | Rollback strategy |
|-------------|------------------------|----------------|-------------------|
| `.drone.star` env vars | All adaptors using the template | Gate by adaptor name if possible; start with SNS | Revert RepoSync MR and trigger sync |
| Dockerfile template | All adaptors using that Dockerfile template | Pilot branch/template variant if supported | Revert template; rebuild affected images |
| `docker-compose.yml` template | All adaptor integration pipelines | Remove one low-risk service only after dependency graph | Revert template and rerun pipeline |
| DIND image update | All pipelines using ACP DIND | ACP canary image/tag if available | Pin previous DIND image/tag |
| Trivy policy change | All scanned images | Start report-only or CRITICAL-only gate | Revert scan flags or add waiver |

Central MRs should include:

- Affected adaptor list.
- Expected before/after behaviour.
- Pilot repo/branch.
- Rollback command or revert plan.
- Evidence required before rollout.

### Appendix J — Security and Compliance Notes

Several proposed optimizations touch security-sensitive areas:

| Area | Security concern | Required control |
|------|------------------|------------------|
| DIND / Docker socket | Privileged container access to Docker daemon | ACP approval and runner isolation confirmation |
| Vault / Drone secrets | Secret exposure in logs or local hooks | No `set -x`; redact output; ACP-managed secrets |
| Registry cache | Cache poisoning or broad write permissions | Dedicated namespace, scoped credentials, retention policy |
| Trivy ignore/gating | Vulnerability waivers can hide risk | Documented waiver owner and expiry |
| Base images | Image provenance and CVE posture | Pin versions/digests where possible |
| Testcontainers private pulls | Auth propagation into test runtime | Confirm Docker auth handling and avoid printing config |

No security approval is required for local-only test prototypes. CI/platform changes should go through ACP/security review where they affect images, runners, secrets, or vulnerability policy.
