## Executive Summary

The `.drone.star` pipeline for `fdp-cmd-adaptor-sns` provides a full CI lifecycle for branch pushes — including Maven build, Docker Compose–based integration tests, Trivy image scan, and Slack notification. Key findings:

- A **CI pipeline** exists for branch pushes and includes build, integration test, Trivy scan, and Slack notification.
- The **`pull_request` event itself produces only a near-empty pipeline** (a single "RepoSync Version" echo step). However, **pushes to feature branches run the full CI pipeline** (build, integration tests, Trivy) via the `push` event, so developers do get CI feedback on their MR branches.
- The **CI Maven step** does not currently set `DOCKER_HOST`, so Testcontainers cannot run in CI without a RepoSync change.
- The **ECR/Artifactory Maven step** already has Testcontainers-related env vars (`DOCKER_HOST`, `TESTCONTAINERS_RYUK_DISABLED`), confirming the pattern works in this Drone/DIND environment.
- **Trivy image scanning exists** but appears report-only (`--exit-code 0`) — vulnerabilities are logged but do not fail the build.
- **Sonar quality/security gate behaviour, dependency scanning, secrets scanning, and vulnerability waiver process** are not visible in the current pipeline and need confirmation.

## 1. Pipeline Types and Purposes

The `main(ctx)` function is the Drone entry point. It inspects `ctx.build.event` and `ctx.build.branch` to decide which pipeline(s) to generate.

| # | Pipeline Name | Trigger | Purpose |
|---|--------------|---------|---------|
| 1 | **CI** | `push` to `develop` or **any non-master branch (incl. feature branches behind MRs)** | Full build, test, scan cycle |
| 2 | **ECR Adaptor** / **ARTIFACTORY Adaptor** | `push` to `develop` (after CI passes) | Build Docker image and publish to registry |
| 3 | **ECR E2E** / **ARTIFACTORY E2E** | `push` to `develop` (after CI passes) | Build and publish end-to-end test image |
| 4 | **CD** | `push` to `develop` (after ECR/Artifactory) | Deploy to `dacc-dde-dev` namespace |
| 5 | **Cleardown** | `push` to `develop` (after CD) | Remove deployed resources from dev |
| 6 | **Deploy** / **Remove** | `promote` event | Deploy or undeploy to a specified namespace |
| 7 | **Tag pipelines** | `tag` event | Build images + deploy to `dacc-dde-test` |
| 8 | **Renew Vault Tokens** | `cron` (`renew-vault-tokens`) | Refresh Vault tokens |
| 9 | **GitLab MR** | `pull_request` event | **Runs, but only a "RepoSync Version" echo step — separate from the branch-push CI** |
| 10 | **push to master** | `push` to `master` | **Runs, but only a "RepoSync Version" echo step — no-op** |

### Pipeline Routing Logic

```text
main(ctx)
├── event == 'push'
│   ├── branch == 'master'       → blank_pipeline('push to master')
│   ├── branch == 'develop'      → CI → ECR/Artifactory → CD → Cleardown
│   └── branch == other          → CI only
├── event == 'pull_request'      → blank_pipeline('GitLab MR')
├── event == 'tag'               → ECR/Artifactory → CD(test) → Cleardown(test)
├── event == 'promote'           → Deploy or Remove (based on target)
├── event == 'cron'              → Renew Vault Tokens
└── else                         → not_implemented_pipeline
```

### Adaptor-Specific Configuration (SNS)

```python
COMMAND_ADAPTOR_NAME = 'sns'
ECR_REPOSITORY = ''                                    # Not using ECR
ARTIFACTORY_REPOSITORY = 'dacc-aws/fdp-cmd-adaptor-sns'  # Using Artifactory
KAFKA_TOPIC_SUFFIX = 'sns'

```

The pipeline has conditional logic for `ctp` (reporting adaptor step) and `sds` (listener step) adaptors — these are inactive for the SNS adaptor.

## 4. Existing Testcontainers Configuration

### ECR/Artifactory Pipeline — Maven Step

```python
{
    'name': 'Maven',
    'image': MAVEN_JAVA17_IMAGE,
    'commands': [
        '. ./set_drone_secrets.sh',
        'mvn clean install',
        'mvn -B dependency:go-offline'
    ],
    'environment': {
        'DOCKER_HOST': 'tcp://docker:2375',
        'TESTCONTAINERS_RYUK_DISABLED': 'true',
        # WORKAROUND: disabling testcontainers reaper processes not compatible with drone
        # https://java.testcontainers.org/features/configuration/#disabling-ryuk
    }
}
```

### Key Observations

1. **Testcontainers has been explored before** — the ECR pipeline explicitly configures it.
2. **Ryuk is incompatible with Drone** — the comment confirms this is a known issue. Ryuk is Testcontainers' container cleanup daemon; disabling it means tests must handle their own cleanup or accept Docker daemon cleanup after the pod terminates.
3. **CI pipeline does NOT have this configuration** — the `mvn clean install` step in `ci_pipeline()` has no `DOCKER_HOST` or `TESTCONTAINERS_*` vars.
4. **The ECR Maven step also runs `mvn -B dependency:go-offline`** — this pre-caches dependencies, suggesting Testcontainers tests may pull additional images.

### Impact

Testcontainers is feasible in this Drone/DIND environment (proven by the ECR pipeline), but CI enablement requires a RepoSync change to add `DOCKER_HOST=tcp://docker:2375` and `TESTCONTAINERS_RYUK_DISABLED=true` to the CI pipeline's `mvn clean install` step environment. Until that change is made, Testcontainers tests can only run locally.

## 5. MR/Pull Request Pipeline Behaviour

### Two separate things happen around an MR

This is the most commonly misunderstood part of the pipeline. There are **two distinct triggers**:

| Trigger | Drone event | Pipeline that runs |
|---------|-------------|--------------------|
| Pushing commits to the feature branch | `push` (branch != master/develop) | **Full CI** — `ci_pipeline()` with build, integration tests, Trivy |
| The merge request object itself | `pull_request` | **`blank_pipeline('GitLab MR')`** — only a "RepoSync Version" echo step |

**In practice, developers DO get full CI feedback on their MR branches** — because every push to the feature branch triggers the full `ci_pipeline()`. GitLab associates those branch-push pipelines with the open MR, which is why you see build and tests running.

### The `pull_request` event specifically runs a near-empty pipeline

```python
elif ctx.build.event == 'pull_request':
    pipelines.append(blank_pipeline('GitLab MR'))
```

```python
def blank_pipeline(name, depends_on=None):
    response = {
        'kind': 'pipeline',
        'name': name,
        'type': 'kubernetes',
        'platform': {'os': 'linux', 'arch': 'amd64'},
        'services': [],
        'steps': []
    }
    response = add_pipeline_step(response, {
        'name': 'RepoSync Version',
        'image': 'alpine:latest',
        'commands': ['echo "RepoSync Version: 7.1.0"']
    })
    return response
```

And the feature-branch push path runs full CI:

```python
elif ctx.build.event == 'push':
    if ctx.build.branch == 'master':
        pipelines.append(blank_pipeline('push to master'))
    elif ctx.build.branch == 'develop':
        pipelines.append(ci_pipeline(ctx))
        # ... + ECR/Artifactory + CD + Cleardown
    else:
        pipelines.append(ci_pipeline(ctx))   # ← feature branches run full CI
```

### Impact

- **CI feedback before merge exists** — it comes from the feature-branch `push` event, not the `pull_request` event.
- The dedicated `pull_request` pipeline is effectively a placeholder (version echo only). Its purpose is unclear and may be intentional or vestigial.
- The full CI on feature branches runs build + integration tests + Trivy, but Sonar runs only on `develop` (see Section 2 — Sonar `when: branch develop`), so static analysis is not part of feature-branch CI.

### Open Question

- Why does the `pull_request` event run a separate near-empty pipeline when branch pushes already cover CI? Is this deliberate (e.g. to avoid duplicate runs) or vestigial? **Needs confirmation with ACP.**

## 9. Slack Notification Behaviour

### Source: `.drone/slack-functions.sh` (Version 1.1)

The CI pipeline sends Slack notifications on `push` to `develop`, `main`, or `master` only (not on feature branches or MRs).

| Function | Channel(s) | Message |
|----------|-----------|---------|
| `send_slack_success` | `fdp-alert-cicd` | `:large_green_circle: Drone Pipeline SUCCESS ...` |
| `send_slack_failure` | `fdp-alert-cicd` + **suspected alarm** | `:large_red_square: Drone Pipeline FAILURE ...` |

### Confirmed Findings

- **Success path:** Posts a green circle message with repo link, build number, and commit author to `fdp-alert-cicd`.
- **Failure path:** Posts a red square message to `fdp-alert-cicd`, then makes a **second call** intended to post to `fdp-alarm-nonprod`.

### Suspected Issue in `send_slack_failure` (Needs Confirmation)

```bash
send_slack_failure() {
  SLACK_APP_TOKEN=$1
  SLACK_CHANNEL="fdp-alert-cicd"
  SLACK_ALARM_CHANNEL="fdp-alarm-nonprod"
  SLACK_TEXT=":large_red_square: ..."
  send_slack_text "${SLACK_CHANNEL}" "${SLACK_TEXT}" "${SLACK_APP_TOKEN}"
  send_slack_text "${SLACK_CHANNEL}" "${SLACK_ALARM_CHANNEL}" "${SLACK_APP_TOKEN}"  # ← suspect
}
```

The second `send_slack_text` call passes:
- Arg 1 (channel): `fdp-alert-cicd`
- Arg 2 (text): `fdp-alarm-nonprod` ← this is a channel name being sent as message text

This appears incorrect. The likely intent was either:
- `send_slack_text "${SLACK_ALARM_CHANNEL}" "${SLACK_TEXT}" "${SLACK_APP_TOKEN}"` (send failure to alarm channel)
- Or some other notification to the alarm channel

> **Status:** Needs confirmation with the team. This may send the literal string "fdp-alarm-nonprod" as a message to `fdp-alert-cicd`, which would be benign but incorrect.

## 11. Trivy Scan Behaviour

### Confirmed Configuration

```bash
trivy image --exit-code 0 --no-progress docker-compose-command-adaptor:latest \
  --severity CRITICAL,HIGH --ignore-unfixed \
  --db-repository acp-zot-helm.acp-zot.svc.cluster.local/ecr/aquasecurity/trivy-db \
  --java-db-repository acp-zot-helm.acp-zot.svc.cluster.local/ecr/aquasecurity/trivy-java-db
```

### Analysis

| Flag | Meaning |
|------|---------|
| `--exit-code 0` | **Always exit successfully** — vulnerabilities are reported but never fail the step |
| `--severity CRITICAL,HIGH` | Only reports CRITICAL and HIGH severity findings |
| `--ignore-unfixed` | Skip vulnerabilities without a published fix |
| `--no-progress` | Suppress progress bar (CI-friendly) |
| `--db-repository` | Uses an internal mirror of the Trivy vuln DB (not pulling from internet) |
| `--java-db-repository` | Uses an internal mirror of the Trivy Java DB |

### Impact

The `--exit-code 0` flag means the Trivy step **can never fail the pipeline**, regardless of the number or severity of vulnerabilities found.

- Vulnerability scanning **exists** in the CI pipeline.
- Vulnerability results are **visible** in Drone build logs.
- Vulnerabilities do **not** act as a release gate — they do not block merge, image publication, or deployment.
- There is no evidence of a vulnerability waiver/exception process in the pipeline configuration itself.

The gap is in release gating, not in the absence of scanning. Whether governance exists outside this pipeline (e.g. Artifactory promotion policies, manual review) needs confirmation.

### What Is Not Visible in the Current Pipeline

| Practice | Status |
|----------|--------|

| Secret scanning (gitleaks, trufflehog) | Not visible in pipeline |
