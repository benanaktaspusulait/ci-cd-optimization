## Key Takeaway

- The adaptor CI pipeline has been mapped step by step.
- Docker/DIND and Docker Compose usage points are now visible.
- The main `mvn clean install` step currently has no `DOCKER_HOST`, so Testcontainers would not work there without a RepoSync-controlled `.drone.star` change.
- Docker Compose is used heavily across infrastructure startup, aggregators, command adaptor startup and integration tests.
- Several optimisation candidates have been identified, but implementation belongs to later tasks.

---

## Evidence Level and Timing Note

This document is a **structural CI map**, not a measured performance baseline.

- Step ordering, commands, DIND usage and Docker Compose commands are based on `.drone.star` and observed pipeline configuration.
- Estimated durations are included only to guide investigation.
- These estimates should not be treated as baseline metrics or proof of improvement potential.
- Real measured timings should be captured from the Drone UI/API in **T2.2 — pipeline baseline**.

---

## Key Findings

- The `mvn clean install` step does not currently expose Docker access via `DOCKER_HOST`.
- Testcontainers in the Maven step would require a RepoSync-controlled `.drone.star` change.
- Docker Compose is invoked multiple times and starts a large dependency graph.
- There may be duplicate Maven work between `mvn clean install` and the `integration-tests` compose service running `mvn -Pci-snapshot install`.
- Several DIND steps repeatedly install `docker-compose` and certificates via `apk add`.
- Trivy is currently report-only because it uses `--exit-code 0`.
- CI pipeline and deploy pipeline are separate; this task maps the adaptor CI pipeline only.

### Step 7: mvn clean install

| Property | Value |
|----------|-------|
| Image | `quay.io/ukhomeofficedigital/ileap-java17-mvn:1.3` |
| Environment | None (no DOCKER_HOST!) |
| DIND? | **No** |
| Compose? | No |
| Depends on | Extract Adaptor Information |

**Commands executed:**


**Key observation:** No `DOCKER_HOST` → Maven cannot talk to Docker → Testcontainers would NOT work in this step without a `.drone.star` change.

## 5. Potential Duplicate Work and Inefficiencies

These are **candidate** optimisation areas identified from the pipeline map. They are not yet proven performance issues. T2.2 should provide measured timings before implementation decisions are made.

### 5.1 Double Maven Build

| Build | Step | What it does |
|-------|------|-------------|
| First | `mvn clean install` (step 7) | Compiles all modules, runs unit tests, packages JARs |
| Second | `integration-tests` container (step 10) | Runs `mvn -Pci-snapshot install` with entire repo mounted |

| Aspect | Detail |
|--------|--------|
| **Observation** | The CI Maven step runs `mvn clean install`, then the `integration-tests` compose service runs `mvn -Pci-snapshot install` with the entire repo mounted. |
| **Impact** | Potential duplicate compile/package/test work. This is not proven until the `ci-snapshot` profile and container logs are reviewed. |
| **Ownership / follow-up route** | Repo-local investigation first. If duplicated work is confirmed, follow-up may inform Maven profile changes or integration-test container command changes in later tasks. |

**Question to close:** Does the second build recompile everything, or does it only run integration tests? The `ci-snapshot` profile needs investigation.

### 5.2 Repeated `apk add` in Every DIND Step

Steps 4, 6, 8, 9, 10 all run:

```bash
apk add --no-cache ca-certificates docker-compose && update-ca-certificates
```

| Aspect | Detail |
|--------|--------|
| **Observation** | Multiple DIND-backed steps install `ca-certificates` and `docker-compose` at runtime. |
| **Impact** | Directionally estimated at ~5-10 seconds per step across 5 steps (~25-50 seconds), pending T2.2 timing confirmation. |
| **Ownership / follow-up route** | ACP/DIND image improvement candidate. Baking `docker-compose` and certificates into the DIND image would require ACP/platform ownership. |

### 5.3 Repeated Artifactory Login

Steps 4 and 6 both run:

```bash
echo "$${ARTIFACTORY_PASSWORD}" | docker login -u "$${ARTIFACTORY_USERNAME}" --password-stdin docker.digital.homeoffice.gov.uk
```

| Aspect | Detail |
|--------|--------|
| **Observation** | Artifactory Docker login is performed in more than one DIND step. |
| **Impact** | Likely minor (~2 seconds each), and may be acceptable unless measured timings show otherwise. It may also be intentional because step/container state boundaries are not guaranteed. |
| **Ownership / follow-up route** | Minor candidate only. Leave unchanged unless T2.2 timing or reliability data shows it matters. |

### 5.4 Sequential Wait Checks

Step 10 (Integration Tests) runs `pre-integration-test` twice sequentially:

- Once with `WAIT_CHECK=command_adaptor`
- Once with `WAIT_CHECK=aggregators`

| Aspect | Detail |
|--------|--------|
| **Observation** | Integration Tests runs two blocking wait checks sequentially before executing the test container. |
| **Impact** | Potential wait-time duplication, but changing it may affect readiness guarantees. |
| **Ownership / follow-up route** | Needs dependency/risk analysis before changing. T5.1/T5.2 service mapping and T2.2 timings should inform whether this is worth optimising. |

### 5.5 Trivy Is Report-Only (Does Not Act as a Release Gate)

`trivy image --exit-code 0` means the Trivy step **always succeeds**, regardless of vulnerabilities found.

- CRITICAL and HIGH findings are **logged** in Drone build output
- They do **not** fail the build, block the merge, or prevent image publication
- The gap is in **release gating/governance**, not in the absence of scanning
- Vulnerability scanning exists; enforcement does not (in the pipeline)

| Aspect | Detail |
|--------|--------|
| **Observation** | Trivy scans CRITICAL/HIGH vulnerabilities but uses `--exit-code 0`, so findings are report-only. |
| **Impact** | Vulnerabilities are visible in logs but do not fail the CI pipeline or block publication. This is a governance/security posture question, not an immediate functional bug. |
| **Ownership / follow-up route** | Security/governance decision. Any gating change should be agreed with ACP/security and likely implemented through RepoSync/pipeline changes. |

This report-only mode can be a deliberate adoption pattern (scan → report → build governance later). See T1.1 Section 11 for full analysis.

### 5.6 Aggregators Reads `CORE_TAG.env` Without Depending on the Step That Creates It

| Aspect | Detail |
|--------|--------|
| **Observation** | The **Aggregators** step runs `source CORE_TAG.env` and then pulls aggregator images tagged `${CORE_TAG}`. However, `CORE_TAG.env` is written by the **mvn clean install** step (its first commands extract `aggregator-core.version`). The Aggregators step's `depends_on` is `['Extract Adaptor Information', 'Kafka & Redis']` — it does **not** list `mvn clean install`. |
| **Impact** | No dependency guarantees `CORE_TAG.env` exists before Aggregators reads it. If Aggregators ran before mvn wrote the file, `CORE_TAG` would be empty and aggregator images could resolve to an invalid/empty tag. In practice the long Kafka & Redis wait (~60-120s) likely lets mvn write the file first, so this may not surface — but it is a latent ordering risk, not an enforced guarantee. |
| **Ownership / follow-up route** | **Needs confirmation.** Verify from real run logs whether `CORE_TAG.env` is reliably present when Aggregators runs. If it is a real race, the fix (adding a dependency, or moving CORE_TAG extraction into an earlier shared step) is a RepoSync `.drone.star` change. |

> **Status:** Source-confirmed that the `mvn clean install` dependency is absent from the Aggregators step; runtime impact needs confirmation from pipeline logs.

## 6. CI vs Deploy Pipeline Boundary

| Concern | CI Pipeline (pilot scope) | Deploy Pipeline (NOT in scope) |
|---------|--------------------------|-------------------------------|
| **Repo** | Per-adaptor repo (e.g. `fdp-cmd-adaptor-sns`) | MMA service repo |
| **Trigger** | Push to branch / tag | Promote event / push to service repo |
| **Output** | Docker image + Helm chart in Artifactory | Deployed pods in Kubernetes |
| **Steps** | Build, test, scan, publish | Helm package, lint, template, deploy |
| **Ownership** | CST + ACP (pipeline) | CST + Platform |

The CI pipeline ends when the Docker image and Helm chart are published to Artifactory. Everything after that is the deploy pipeline's responsibility.
