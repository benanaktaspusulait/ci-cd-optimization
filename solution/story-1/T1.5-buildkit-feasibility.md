## Key Takeaway

BuildKit optimisation splits into three tiers of confidence:

- **Local optimisation is safe to start now** — multi-stage Dockerfile, `.dockerignore`, `DOCKER_BUILDKIT=1`, and `RUN --mount=type=cache` all work on developer machines and can be prototyped immediately by CST (Story 3).
- **Basic CI BuildKit support is likely but unproven** — the ACP DIND image probably runs a recent enough Docker to support `DOCKER_BUILDKIT=1` and cache mounts, but this must be confirmed with the smoke validation below before being treated as fact.
- **Registry (remote) cache requires ACP** — persistent cache between CI runs needs a cache namespace, push/pull credentials, retention policy, and `.drone.star` changes. It is a long-term optimisation, not a Story 3 prerequisite.

Multi-stage builds and `.dockerignore` deliver the bulk of the local benefit with no platform dependency. Cache mounts help within a single build but are ephemeral in Drone/DIND until registry cache exists.

## BuildKit vs buildx

BuildKit is the Docker build engine. It can be enabled for standard Docker builds with:

```bash
DOCKER_BUILDKIT=1 docker build
```

`docker buildx` is a CLI plugin that exposes advanced BuildKit features, including builder instances, multi-platform builds, and advanced cache export/import options.

Registry cache options such as `--cache-to=type=registry` and `--cache-from=type=registry` normally require `docker buildx build`. Therefore, missing `buildx` does not automatically block basic BuildKit usage, but it does block advanced registry cache usage.

### Q3: Can `--mount=type=cache` work inside the DIND daemon?

**Finding: LIKELY YES if BuildKit is enabled — ephemeral in Drone/DIND until validated.**

| Scenario | Cache Behaviour |
|----------|----------------|
| Within a single pipeline run | ✅ Cache persists between stages of a multi-stage build |
| Between two `docker build` commands in same pipeline | ✅ Cache persists (same DIND daemon) |
| Between pipeline runs | ❌ Cache is lost (new DIND pod each time) |
| Local developer machine | ✅ Cache persists between builds |

**Use case:** Cache mounts are useful for Maven dependency caching **within a multi-stage build**:

```dockerfile
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2/repository mvn dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2/repository mvn package -DskipTests
```

In CI, this cache helps **within** the build (dependency download → compile stages) but is empty on next pipeline run.

**Validation required:** `RUN --mount=type=cache` depends on BuildKit support and Dockerfile frontend syntax support. It should be validated with a minimal Dockerfile in Drone before being treated as confirmed.

**Local benefit:** On developer machines, cache persists indefinitely — significant speed improvement for repeated builds.

## 5. Current Dockerfile Analysis (Optimisation Potential)

Current `cmd-adaptor-sns/Dockerfile`:

```dockerfile
FROM amazoncorretto:17            # Full JDK — ~470MB base

COPY ./target/cmd-adaptor-sns-exec.jar /local
COPY ./target/dependencies/opentelemetry-javaagent.jar /local/opentelemetry-javaagent.jar

RUN yum install -y shadow-utils unzip \
    && yum update -y [many packages] \
    && yum erase -y vim-data \
    && curl ... envconsul ... \
    && adduser fdpuser \
    && chmod/chown ...

USER fdpuser
CMD ["java", "-javaagent:...", "-jar", "/local/cmd-adaptor-sns-exec.jar"]
```

**Problems:**
1. **Full JDK as runtime base** — `amazoncorretto:17` includes JDK (compiler, tools) that may not be needed at runtime. A smaller runtime image could help, but the candidate base image must be validated for compatibility and security approval.
2. **No multi-stage build** — build artefacts (JAR) are assumed to exist in `./target/` (built externally by Maven step). The Dockerfile is a simple copy + setup.
3. **Monolithic RUN** — single large RUN with yum install, update, download, user creation. Layering could be improved.
4. **No `.dockerignore`** — build context may include unnecessary files.
5. **yum update in build** — `yum update -y` improves patch freshness but makes builds less deterministic. A preferred long-term model is to use an approved, regularly rebuilt patched base image rather than updating packages unpredictably inside each application Dockerfile.

**Multi-stage opportunity (local proposal):**

```dockerfile
# Stage 1: Runtime base (no build tools needed — JAR is pre-built by Maven)
FROM <approved-java-17-runtime-base> AS runtime
# Candidate examples must be validated before use:
# - Amazon Corretto 17 slim/JRE-style base, if approved
# - Organisation-maintained Java runtime base, if available
# - Alpine-based images only after musl/glibc compatibility checks

RUN adduser -D -u 1000 fdpuser
COPY --chown=fdpuser:fdpuser target/cmd-adaptor-sns-exec.jar /local/
COPY --chown=fdpuser:fdpuser target/dependencies/opentelemetry-javaagent.jar /local/

USER fdpuser
CMD ["java", "-javaagent:/local/opentelemetry-javaagent.jar", "-jar", "/local/cmd-adaptor-sns-exec.jar"]
```

**Runtime base caution:** Alpine-based Java images can be smaller, but Alpine uses musl rather than glibc. That can introduce compatibility differences for native libraries, monitoring agents, certificates, shell tooling, or operational scripts. Prefer approved organisation base images where available.

**Size reduction expectation:** Indicative size reduction may be significant, but must be measured using the actual approved runtime base image and the current application artefact.

**Ownership note:** The production Dockerfile is RepoSync-controlled per T1.2, so production changes must go through a RepoSync MR. `.dockerignore` ownership still needs confirmation before deciding whether it is a repo-local MR or a central template change.
