## Key Takeaway

- Testcontainers can be piloted locally without RepoSync or ACP changes.
- CI execution appears feasible because the Drone pipeline already uses DIND and the ECR Maven step has precedent for `DOCKER_HOST` and `TESTCONTAINERS_RYUK_DISABLED`.
- The main CI `mvn clean install` step does not currently expose `DOCKER_HOST`, so Testcontainers will not work there without a RepoSync-controlled `.drone.star` change.
- CI feasibility should be treated as **likely feasible with constraints**, but not fully proven until a Drone smoke test confirms Docker access from the Maven step.
- Story 4 should proceed local-first; CI enablement should be a separate RepoSync/ACP follow-up.

## 1. Investigation Questions & Findings

### Q1: Can the `mvn clean install` step access DOCKER_HOST?

**Finding: NO — not currently configured.**

The CI pipeline's `mvn clean install` step (step 7) does **not** set `DOCKER_HOST`:

```python
# ci_pipeline() — mvn clean install step
{
    'name': 'mvn clean install',
    'image': MAVEN_JAVA17_IMAGE,
    'commands': [
        '. ./set_drone_secrets.sh',
        # ... CORE_TAG extraction ...
        'mvn clean install'
    ],
    'depends_on': ['Extract Adaptor Information']
    # No 'environment' block — no DOCKER_HOST
}
```

**However**, the ECR pipeline's Maven step **does** have it:

```python
# ecr_pipeline() — Maven step
'environment': {
    'DOCKER_HOST': 'tcp://docker:2375',
    'TESTCONTAINERS_RYUK_DISABLED': 'true',
}
```

The ECR Maven step provides strong precedent that Maven steps can be configured to reach DIND. The main CI Maven step is not currently configured with `DOCKER_HOST`, so direct reachability from the main CI Maven step should be validated with a smoke test after RepoSync env vars are added.

---

### Q2: Does `TESTCONTAINERS_RYUK_DISABLED=true` need to be set?

**Finding: YES — required.**

The ECR pipeline has an explicit comment:

```python
'TESTCONTAINERS_RYUK_DISABLED': 'true',
# WORKAROUND: disabling testcontainers reaper processes not compatible with drone
# https://java.testcontainers.org/features/configuration/#disabling-ryuk
```

**Why Ryuk fails in Drone:**
- Ryuk is a sidecar container that Testcontainers starts to clean up test containers after the JVM exits
- Ryuk needs to connect back to the Docker daemon and monitor container lifecycle
- In Drone's DIND setup, the Docker daemon runs in a separate service pod — Ryuk's networking assumptions don't hold
- With Ryuk disabled, containers are cleaned up when the DIND pod terminates (which happens at pipeline end)

**Cleanup implications:**
- Within a single pipeline run: orphaned containers accumulate in DIND if tests fail mid-run
- Between pipeline runs: no issue — each run gets a fresh DIND pod
- **Risk is LOW** — pod termination provides a natural cleanup boundary

---

### Q3: Is `TESTCONTAINERS_CHECKS_DISABLE=true` needed?

**Finding: RECOMMENDED but not strictly required.**

Testcontainers pre-flight checks test:
- Docker daemon reachability
- Docker API version compatibility
- Disk space availability

In Drone DIND, these checks may produce false warnings (e.g., disk space on ephemeral pod). Disabling them avoids unnecessary noise and startup delay (~1-2s).

---

### Q4: Can Testcontainers pull images through DIND?

**Finding: LIKELY for public images — private-registry auth needs validation.**

The pipeline already logs into Artifactory in step 4 (Kafka & Redis):
```bash
echo "$${ARTIFACTORY_PASSWORD}" | docker login -u "$${ARTIFACTORY_USERNAME}" --password-stdin docker.digital.homeoffice.gov.uk
```

However, this login happens in a **different step** (different container). `docker login` writes credentials **client-side** (to `$HOME/.docker/config.json` or `$DOCKER_CONFIG` in the step container that runs it), not into the DIND daemon. Because each Drone step runs in its own container, the Maven step would **not automatically inherit** step 4's login unless the Docker config is shared via the workspace or `DOCKER_CONFIG`. This means private-registry pulls from the Maven step should not be assumed to work and must be validated.

**For public images** (Redis, Kafka from Docker Hub / Confluent): safest first candidate. Redis is the recommended smoke-test image because it avoids private registry auth assumptions.

However, even public image pulls depend on CI network, proxy and allowlist policy. If Docker Hub access is blocked or rate-limited, retry the smoke test with an approved internal mirror of Redis. Do not interpret a Docker Hub pull failure as a Testcontainers failure until network and proxy restrictions are ruled out.

**For private images** (aggregators from `docker.digital.homeoffice.gov.uk`): the Maven step would likely need its own registry auth. Do not assume the step 4 login carries over.

**Private registry authentication decision path:**

1. Start with a public Redis image.
2. If the public image works, record Docker reachability and basic Testcontainers feasibility.
3. If the public image is blocked, retry using an approved internal Redis mirror.
4. If private application images are needed later, do not rely on a previous Drone step's `docker login`.
5. Use one of:
   - fresh `docker login` inside the Maven/Testcontainers step
   - shared workspace `DOCKER_CONFIG`
   - `TESTCONTAINERS_DOCKER_AUTH_CONFIG`
   - an approved registry mirror
6. Treat private image support as a separate validation item, not part of the minimal CI smoke test.

**Testcontainers-specific registry config:** Keep `TESTCONTAINERS_DOCKER_AUTH_CONFIG` as an investigation item if private images are needed.

### Q5: Is there a Drone step timeout risk?

**Finding: LOW RISK for a small pilot.**

- No explicit step timeout was found in `.drone.star`
- Drone server or runner defaults may still apply
- Testcontainers typical startup: 5-30 seconds per container
- Current integration test step already runs 2-4 minutes without timeout issues
- The first pilot should use a lightweight dependency such as Redis to avoid creating timeout noise

**Note:** The `deploy_pipeline` uses `--timeout 15m` for kd deployments, but CI steps have no explicit timeout.

---

### Q6: Would Testcontainers conflict with existing docker-compose?

**Finding: NO CONFLICT — if properly scoped.**

| Aspect | Docker Compose (current) | Testcontainers (proposed) |
|--------|-------------------------|--------------------------|
| Runs in | DIND steps (separate containers) | Maven JVM (step 7 or a new step) |
| Docker daemon | Same DIND | Same DIND |
| Port allocation | Fixed ports (6379, 9092, etc.) | Random ports (Testcontainers default) |
| Container naming | Fixed names (`redis`, `kafka`) | Random names |
| Lifecycle | Runs across multiple steps | Starts/stops within test methods |

**Potential conflict:** If both Compose services AND Testcontainers try to start the same dependency (e.g., two Redis instances), port conflicts on fixed ports could occur.

**Mitigation:** Testcontainers uses random port mapping by default. As long as test code uses `container.getMappedPort()` instead of hardcoded ports, no conflict.

**Recommended approach:** Run Testcontainers tests in dedicated Maven profiles that do **not** depend on existing Compose services. Prefer separate names such as `local-testcontainers` for developer-machine tests and `ci-testcontainers-smoke` for the minimal Drone smoke test. The team can change the exact names, but keeping local development and CI smoke validation separate is useful because they have different constraints.

Do not try to replace the full Compose stack in T1.4. Compose reduction belongs to Story 5 after service mapping and Testcontainers findings are available.

## 2. Required Environment Variables for CI

If Testcontainers is to run in the CI pipeline's Maven step, the following env vars must be added:

```python
'environment': {
    'DOCKER_HOST': 'tcp://docker:2375',
    'TESTCONTAINERS_RYUK_DISABLED': 'true',
    'TESTCONTAINERS_CHECKS_DISABLE': 'true',  # recommended
}
```

**Security note:** `DOCKER_HOST=tcp://docker:2375` should only be used inside the isolated Drone/DIND pipeline network. It must not be exposed outside the pipeline context. This assessment assumes the Docker daemon is scoped to the ephemeral Drone job/DIND service and is not shared across unrelated jobs.

**Optional / investigate:**
```python
    'TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE': '/var/run/docker.sock',  # may not be needed with tcp://
```

## 7. Two-Layer Docker Compose Orchestration (Drone vs Maven Plugin)

> **Context:** A reviewer noted that integration tests are orchestrated by docker-compose at two layers — the Drone CI pipeline and the Maven `docker-compose-maven-plugin`. This section verifies that observation against source and assesses the architectural implications. Note: the orchestration-ownership decision and any migration belong to **Story 5 (Compose Rationalisation)**; this section documents the finding because it directly affects whether/how Testcontainers can replace the setup.

### 7.1 Confirmed: Two Orchestration Mechanisms Exist

| Layer | Where | How |
|-------|-------|-----|
| **Drone CI (pipeline level)** | `.drone.star` CI steps | Runs `docker-compose ... up` directly via the DIND service in steps Kafka & Redis, Aggregators, Command Adaptor, Integration Tests |
| **Maven (build level)** | `cmd-adaptor-sns-integration-tests/pom.xml` | `com.dkanejs.maven.plugins:docker-compose-maven-plugin:4.0.0`, bound to `pre-integration-test` (up), `post-integration-test` (down), `clean` (down) |

Both drive the **same** `docker-compose.yml`.

### 7.2 Important Nuance: The Two Layers Are Mutually Exclusive by Environment

The reviewer's "duplication and coupling" is correct, but the layers do **not** run simultaneously or conflict at runtime. They are gated by Maven properties `skip.containers` and `skip.aggregators`:

| Profile | `skip.containers` | `skip.aggregators` | Who orchestrates compose |
|---------|:-----------------:|:------------------:|--------------------------|
| `local` (default) | true | true | Neither (tests skipped) |
| `local-int-cmd` | false | true | **Maven plugin** (cmd only) |
| `local-int-snapshot` | false | false | **Maven plugin** (full stack) |
| `ci-cmd` | true | true | **Drone** (plugin skipped) |
| `ci-snapshot` (CI) | true | true | **Drone** (plugin skipped) |

So in **CI** (`ci-snapshot`), the Maven plugin executions are all skipped — Drone owns the lifecycle. **Locally** (`local-int-*`), the Maven plugin owns it and Drone is not involved. There is therefore no double-startup or port conflict *between the two layers* within a single run.

### 7.3 Lifecycle Map

**CI (`ci-snapshot`, plugin skipped — Drone owns lifecycle):**
```
Drone: Kafka & Redis step      → docker-compose up pre-integration-test (WAIT_CHECK=redis_kafka)
Drone: Aggregators step        → docker-compose up -d (6 aggregators, NO v1id-v2id)
Drone: Command Adaptor step    → docker-compose up --build command-adaptor (detached)
Drone: Integration Tests step  → wait command_adaptor, wait aggregators, then
                                  docker-compose up integration-tests
                                    └─ container runs `mvn -Pci-snapshot install`
                                       (skip.containers=true → plugin does NOT start compose)
```

**Local (`local-int-snapshot`, Maven owns lifecycle):**
```
mvn install -Plocal-int-snapshot
 └─ pre-integration-test phase (docker-compose-maven-plugin):
      up pre-integration-test (WAIT_CHECK=redis_kafka)
      up 7 aggregators (incl. v1id-v2id)  [CORE_TAG=${aggregator-core.version}]
      up pre-integration-test (WAIT_CHECK=aggregators)
      up command-adaptor
      up pre-integration-test (WAIT_CHECK=command_adaptor)
 └─ integration-test phase (failsafe): run *IntegrationTest
 └─ post-integration-test phase: docker-compose down
```

### 7.4 Real Duplication, Coupling and Divergences (Source-Verified)

| Issue | Detail |
|-------|--------|
| **Duplicated startup/wait logic** | The `WAIT_CHECK=redis_kafka / aggregators / command_adaptor` sequencing is encoded **twice** — once as Drone step commands, once as Maven plugin executions. Both must be kept in sync by hand. |
| **Coupling to compose service names** | Both layers hardcode the same service names; renaming a service in `docker-compose.yml` requires edits in both `.drone.star` and `pom.xml`. |
| **Aggregator set divergence** | Drone starts **6** aggregators (no `v1id-v2id`); the Maven plugin starts **7** (includes `aggregate-v1id-v2id`). Local and CI therefore exercise slightly different topologies. |
| **`CORE_TAG` resolved differently** | Drone derives `CORE_TAG` via `mvn help:evaluate` into `CORE_TAG.env`; the Maven plugin passes `CORE_TAG=${aggregator-core.version}` as a property. Two code paths for the same value → version-skew risk. |
| **Lifecycle teardown only on one side** | The Maven plugin has explicit `down` on `post-integration-test`/`clean`. The Drone path relies on DIND pod teardown at pipeline end (no explicit `down`). |

### 7.5 Which Layer Should Own Lifecycle?

This is a Story 5 decision, but the evidence points to:

- **CI:** Drone already owns it (plugin skipped). Keep a single owner per environment.
- **Local:** The Maven plugin is developer convenience. This is the layer Testcontainers can most cleanly replace first (developer-owned, no RepoSync dependency).
- **Avoid** maintaining both as the long-term model. The duplication is a maintenance/divergence cost, not a runtime conflict.

### 7.6 Could Testcontainers Replace This Setup?

| Service class | Testcontainers fit | Note |
|---------------|:------------------:|------|
| Infra (Kafka, Zookeeper, Schema Registry, Redis, LocalStack) | Good | Standard modules / `GenericContainer`; per-test isolation, random ports |
| Custom apps (6–7 aggregators, command-adaptor) | Poor | Bespoke FDP images; would need `GenericContainer` wiring and the right `CORE_TAG`; effort is high |
| Test runner (`integration-tests`) | N/A | Becomes the JVM running the tests |

**Assessment:** Testcontainers can realistically replace the **local Maven-plugin layer for infrastructure services first** (collapsing local orchestration to a single model in code), while the aggregators/command-adaptor and the CI Drone layer remain until Story 5 decides the target. Full replacement of both layers is a larger effort and is not proven here.

### 7.7 Risks in the Current Two-Layer Setup

| Risk | Source-verified? | Detail |
|------|:----------------:|--------|
| Local vs CI topology drift | Yes | 6 vs 7 aggregators; tests can pass locally but behave differently in CI (or vice versa) |
| `CORE_TAG` version skew | Yes | Two resolution paths can disagree if the property and the help-plugin output diverge |
| State leakage / no isolation | Yes | `docker-compose.yml` uses fixed `container_name`, fixed host ports, and `restart: always` — shared, non-isolated state across runs on a persistent host (local dev especially) |
| Ordering race (`CORE_TAG.env`) | Yes | See T1.3 §5.6 — Drone Aggregators step reads `CORE_TAG.env` without depending on the step that writes it |
| Maintenance divergence | Yes | Two places encode the same startup/wait logic; easy to update one and miss the other |
| Flakiness from shared fixed ports | Partial | Fixed host ports (6379, 9092, …) prevent parallel runs on the same host; impact depends on runner model — needs confirmation |

> **Scope note:** This section documents architecture and risk. The orchestration-ownership decision, simplified single-model target, and step-by-step migration plan are owned by **Story 5**, informed by T1.3 (CI step map), T1.4 (this Testcontainers assessment) and T5.1/T5.2 (service mapping).

## Appendix: Example Minimal Redis Smoke Test

This example is illustrative only and avoids project-specific assumptions. It uses a random host port assigned by Docker and reads that port through Testcontainers rather than hardcoding `6379` on the host.

```java
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertTrue;

import org.junit.jupiter.api.Test;
import org.testcontainers.containers.GenericContainer;
import org.testcontainers.utility.DockerImageName;

class MinimalRedisTest {

    @Test
    void startsRedisContainer() {
        try (GenericContainer<?> redis = new GenericContainer<>(DockerImageName.parse("redis:7-alpine"))
                .withExposedPorts(6379)) {
            redis.start();

            String redisHost = redis.getHost();
            Integer redisPort = redis.getMappedPort(6379);

            assertTrue(redis.isRunning());
            assertFalse(redisHost.isBlank());
            assertTrue(redisPort > 0);
        }
    }
}
```
