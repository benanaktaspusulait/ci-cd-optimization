### 4.2 Orchestration relationships not encoded by `depends_on`

- `command-adaptor` has no Compose dependency. Drone and Maven ordering start infrastructure before it.
- `integration-tests` has no Compose dependency. Drone runs readiness checks before starting it.
- `aggregate-matching` and `aggregate-v1id-v2id` reference Redis and Jaeger through environment without declaring those dependencies.
- List-form `depends_on` establishes startup ordering, not application readiness.
- `pre-integration-test/app.py` supplies readiness behaviour:
  - `redis_kafka`: ping Redis, wait for Schema Registry and Kafdrop, then create Kafka topics
  - `command_adaptor`: wait for command-adaptor health
  - `aggregators`: wait for event, location, object, party and service aggregate readiness
- The readiness code does not check `aggregate-matching` or `aggregate-v1id-v2id`.

## 7. Confirmed Facts

- The inspected Compose file defines exactly 20 services.
- All services use the implicit default Compose network.
- The mapped Drone path involves 17 services; three are not invoked there.
- CI starts six aggregators; `local-int-snapshot` starts seven.
- The local Maven and Drone paths use the same Compose file but separate lifecycle orchestration.
- Kafka and Schema Registry are directly used by the Java E2E producer/consumer and Avro client configuration.
- Kafdrop is not merely present: current readiness code actively waits for its health endpoint.
- The local topic-export script explicitly invokes `kafka-topic-extract`.
- No mapped invocation of `kafka-rest` was found.
- Story 4 confirms only that Redis can be exercised independently for a narrow smoke/wiring test. It does not establish removal of Redis, Kafka, Schema Registry or any other service from full E2E.

## 8. Structural Observations

- Current CI behaviour depends on both explicit Drone commands and transitive Compose dependencies.
- Current local E2E behaviour depends on Maven plugin executions and profile flags.
- `command-adaptor` and `integration-tests` rely on external orchestration ordering rather than Compose dependencies.
- Kafdrop is coupled into readiness through both `pre-integration-test.depends_on` and an explicit HTTP wait.
- Jaeger is wired as the OTEL endpoint for the command adaptor and aggregators, but no automated trace assertion was found.
- LocalStack is explicitly started in CI, but the inspected SNS test code does not establish that it is part of the core Kafka assertion path.
- The README mentions Confluent Control Center on port `9021`, but the inspected Compose file defines no Control Center service. This is documentation/configuration drift, not evidence of a running service.
- Fixed container names, fixed host ports and `restart: always` make the default Compose topology shared-host oriented rather than isolated per test.

## 9. Inferences and Unresolved Questions

### Inferences

- Kafdrop and Jaeger appear useful for inspection/observability, but local developer use was not explicitly documented in the inspected README files.
- `kafka-rest` appears intended as an optional API/debug utility from its image and exposed port, but no invocation was found.
- LocalStack may be retained by shared RepoSync topology rather than current SNS assertions; this requires confirmation.

### Unresolved questions

- Is Kafdrop functionally required, or is its readiness check a convenience inherited from the shared startup flow?
- Would removing Jaeger affect application startup or only telemetry visibility?
- Does the current SNS CI/E2E path use LocalStack after the explicit wait step?
- Which snapshot scenarios require `aggregate-matching`?
- Why does local `local-int-snapshot` start `aggregate-v1id-v2id` while CI does not?
- Should readiness also check `aggregate-matching` and `aggregate-v1id-v2id`, or are they intentionally excluded?
- Is `kafka-rest` used by an undocumented manual workflow?
- Is the stale Control Center README reference still expected by developers?
- Which owner controls durable changes to the RepoSync-managed Compose and pre-integration files?
