## Recommendation

Retain Compose as the current full-E2E and local-debugging mechanism. Keep the Redis Testcontainers work as an opt-in, isolated local pilot. Treat reductions to CI Compose scope and a single-orchestrator model as follow-up candidates that require equivalent functional validation and the relevant RepoSync/platform decision.

| Area | Recommendation | Evidence status |
|---|---|---|
| Full E2E custom applications | Retain current Compose coverage | Current structural dependency |
| Local full-stack/debugging tools | Retain where useful | Current workflow; no replacement assessed |
| Redis-only isolated tests | Retain opt-in Testcontainers pilot | Two local functional runs; no Compose performance comparison |
| Kafka/Schema Registry/LocalStack | Keep current defaults; assess separately | Not piloted |
| Kafdrop/Jaeger in CI | Retain pending equivalent validation; investigate as reduction candidates | Functional and timing impact `not measured` |
| Single orchestration owner | Retain as an architectural candidate | Requires CST design plus RepoSync/platform decision |
| Reduced CI Compose configuration | Do not adopt from current evidence | No like-for-like CI or full-E2E validation |

## Target boundary

```text
Isolated dependency pilot  -> opt-in Testcontainers where measured
Full E2E / custom apps     -> current Compose path retained
Local debugging            -> Compose and debug tools retained
Durable CI change          -> equivalent validation + RepoSync/platform route
```

This boundary avoids a permanent claim that the Redis pilot replaces the full stack. It also avoids presenting the two existing orchestration paths as already reconciled.

## Required evidence before reduction

- Equivalent functional runs for the exact scope being changed.
- Full-E2E validation when custom applications or readiness utilities are affected.
- Separate Redis-only, Kafka/Schema Registry and full-E2E measurements.
- CI execution evidence before any CI saving claim.
- Repeated rerun evidence before any flaky-test or reliability claim.
- Owner confirmation for RepoSync-controlled Compose or pipeline changes.

## Ownership and adoption route

| Change | Technical owner / input | Durable route |
|---|---|---|
| Repo-local opt-in test code | CST | Normal repository review; remains non-default until approved |
| Compose/pipeline template change | RepoSync/platform with CST evidence | Owner decision and RepoSync change route |
| Shared Testcontainers pattern | Wider platform/engineering enablement if pursued | Separate prioritisation after repository evidence |
| Temporary target-repository experiment | CST may use it for evidence if authorised | Must be re-expressed through the durable owner; not production adoption |

## Architectural decision

Story 1 found two container-lifecycle owners: Drone in CI and Maven/Compose locally. A single entry point such as `mvn verify` remains a candidate because it could improve local/CI parity, but the pilot has not implemented or validated that cutover. The owner must choose the target before Compose reduction is designed; technical feasibility does not grant permission to change RepoSync-controlled behaviour.

## Claims and non-claims

Claimed:

- The current configuration and invocation paths can be mapped and classified.
- A Redis Testcontainers smoke/wiring pilot works locally in its opt-in scope.
- Compose remains necessary for the current full-E2E/custom-application flow.

Not claimed:

- No Compose service reduction has been implemented.
- No CI, startup, flaky-test or developer-feedback improvement is claimed.
- No Kafka/Schema Registry or broad infrastructure migration is validated.
- No default Maven, Compose or pipeline behaviour changed.
- No stakeholder, RepoSync/platform or production approval is recorded.

## Decision

Keep the present full-E2E and local Compose paths. Continue the isolated Redis pilot only within its measured scope. Carry CI Compose reduction and single-orchestrator design into Story 6 as ownership/adoption candidates, not approved changes.
