## 1. Recommendation

### Docker Compose should be retained for:

1. **Custom application services** (aggregators, command-adaptor) — these are FDP-specific Java applications that cannot be replaced by standard Testcontainers modules
2. **Local debugging workflows** — Kafdrop, Jaeger UI, kafka-rest provide valuable developer tooling
3. **Full end-to-end integration tests** — tests that validate the complete message flow through all services

### Docker Compose should be reduced/removed from:

1. **CI infrastructure services** — Kafka, Redis, Schema Registry, LocalStack can be managed by Testcontainers within the Maven JVM
2. **CI-only utility containers** — kafdrop, jaeger in CI serve no functional purpose
3. **Wait containers** — Testcontainers has built-in wait strategies; `pre-integration-test` and `wait4localstack` become unnecessary for TC-managed services

## 2. Proposed Future State

### CI Pipeline (after Testcontainers enabled)

```
BEFORE (current):
├── Kafka & Redis step (compose: 9 services started)
├── Aggregators step (compose: 6 services)
├── Command Adaptor step (compose: 1 service built + started)
├── Integration Tests step (compose: wait checks + test runner)
└── Total: ~17 compose services

AFTER (with Testcontainers for infra):
├── mvn clean install (Testcontainers starts Redis, Kafka, SR, LocalStack inside Maven)
├── Aggregators step (compose: 6 services — still needs CORE_TAG images from Artifactory)
├── Command Adaptor step (compose: 1 service built + started)
├── Integration Tests step (for full-stack Cucumber tests that need aggregators)
└── Total: ~8 compose services
```

### Local Development

```
KEEP docker-compose for:
├── Full stack debugging (all services + Kafdrop + Jaeger)
├── End-to-end scenario testing
├── Manual exploratory testing
└── Onboarding new developers (one command: docker-compose up)

USE Testcontainers for:
├── Fast isolated unit-integration tests (mvn verify -Ptestcontainers)
├── TDD workflow (change → test in <30s)
└── CI-level tests that only need infrastructure
```

## 3. Compose File Evolution

### Option A: Single file, profile-based (Docker Compose profiles)

```yaml
services:
  # Infrastructure — always available
  kafka:
    profiles: ["full", "infra"]
    ...
  redis:
    profiles: ["full", "infra"]
    ...
  
  # Application — only for full stack
  aggregate-matching:
    profiles: ["full"]
    ...
  command-adaptor:
    profiles: ["full", "app"]
    ...
  
  # Debug tools — only local
  kafdrop:
    profiles: ["debug"]
    ...
  jaeger:
    profiles: ["full", "debug"]
    ...
```

Usage: `docker-compose --profile full up` or `docker-compose --profile debug up`

### Option B: Separate compose files (cleaner separation)

```
docker-compose.yml              → Core services (infra + apps)
docker-compose.debug.yml        → Debug tools (kafdrop, jaeger, kafka-rest)
docker-compose.ci.yml           → CI-only overrides (remove debug services)
```

### Recommendation: Option A (profiles)

- Single file to maintain
- Clear which services belong to which scenario
- Compatible with existing RepoSync structure

## 4. Transition Plan

| Phase | Compose Role | Testcontainers Role | CI Impact |
|-------|-------------|--------------------|-----------| 
| **Current** | Everything (infra + apps + debug + tests) | Nothing | Full compose orchestration in pipeline |
| **Phase 1** | Everything (unchanged) | New isolated tests alongside | No CI change; TC tests run locally only |
| **Phase 2** | Apps + debug | Infra for new tests | CI: add DOCKER_HOST to Maven step (RepoSync MR) |
| **Phase 3** | Apps only (CI); Apps + debug (local) | All infra | CI: remove Kafka & Redis compose step; add TC env vars |

### Phase 3 Pipeline (target state):

```
RepoSync Version → Secrets → Wait for Docker →
Extract Info → Aggregators (compose: 6 services) →
mvn clean install (with DOCKER_HOST — TC starts infra) →
Command Adaptor (compose: 1 service) →
Integration Tests (compose: full-stack Cucumber only) →
Sonar → Trivy → Slack
```

**Steps removed:** "Kafka & Redis" step entirely (infra started by Testcontainers in Maven JVM)
**Time saved:** ~60-120s (infrastructure startup step eliminated)

## 5. What NOT to Remove

| Service | Keep in compose | Why |
|---------|:---------------:|-----|
| Aggregators (6) | ✅ | Custom apps; need real images from Artifactory; can't mock behaviour |
| Command Adaptor | ✅ | System under test; must run as Docker container for realistic testing |
| Kafdrop (local only) | ✅ | Valuable debugging tool; developers inspect topics visually |
| Jaeger (local only) | ✅ | Distributed trace debugging; useful for performance investigation |
| kafka-rest (local only) | ✅ | API access for scripts/debugging |

## 6. Risk Assessment

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Removing infra from compose breaks local debugging | Medium | Keep `docker-compose --profile full up` for full stack; TC is for tests only |
| Aggregators still need compose infra (Kafka, Redis) | High | When TC manages infra in Maven, compose aggregators still need a running Kafka — use same DIND Docker network |
| Docker network conflict (TC random ports vs compose fixed ports) | Medium | TC uses random ports; compose uses fixed ports on different network — no conflict |
| Transition period confusion (which approach to use when) | Low | Clear documentation + Maven profiles (`-Ptestcontainers` vs `-Plocal-int-snapshot`) |

## 8. Architectural Decision: Single Orchestration Owner

> Source: architecture review (Story 1 synthesis). This section records the orchestration-ownership decision that underpins the recommendation above.

### 8.1 The Core Problem (P0)

Container lifecycle currently has **two owners** with no single source of truth:

| Layer | Where | Active when |
|-------|-------|-------------|
| Drone CI (compose CLI in DIND steps) | `.drone.star` | CI (`ci-snapshot` / `ci-cmd` — Maven plugin skipped) |
| Maven `docker-compose-maven-plugin` | `integration-tests/pom.xml` | Local (`local-int-*` — Drone not involved) |

They are mutually exclusive by `skip.containers` / `skip.aggregators`, so they do not conflict at runtime — but the startup/readiness logic is **encoded twice and has already diverged**: Drone starts 6 aggregators, the Maven plugin starts 7 (incl. `v1id-v2id`); `CORE_TAG` is resolved two different ways. Local and CI therefore exercise different topologies. (Cross-ref: T1.3 §5.6, T1.4 §7.)

### 8.2 Recommended Option: Maven owns orchestration in all environments

> **Status: recommendation, not a locked decision.** The ownership choice (Drone vs Maven) is an open architectural decision — see T1.2 "Decision 1 — Options" and the Decision Order, and T6.2 §5. This section records the *recommended* option and its rationale, to be ratified through that decision process.

If adopted, `mvn verify` becomes the single orchestration entry point. Drone shrinks to "provision DIND + run `mvn verify`". The Maven plugin (and, progressively, Testcontainers) owns startup/readiness/teardown everywhere.

**Why Maven, not Drone:**
- `pom.xml` is repo-local (team-owned); `.drone.star` is RepoSync-owned. Moving the single owner to Maven puts orchestration logic where the team can change it.
- Local and CI run the identical path → "passes locally" finally equals "passes in CI".
- Removes the layering inversion (P1-1) where the build is a compose service driven by Drone.

| Trade-off | Detail |
|-----------|--------|
| Pro | Single source of truth; local/CI parity; team-owned orchestration |
| Pro | Eliminates the 6-vs-7 aggregator and dual-`CORE_TAG` divergence |
| Con | Requires `DOCKER_HOST` on the CI Maven step (RepoSync MR) |
| Con | Cutover touches the central compose template + `.drone.star` (ACP coordination) |

### 8.3 Layering Inversion to Remove (P1)

Today the `integration-tests` compose service runs `mvn -Pci-snapshot install` with the repo bind-mounted — so Maven is sometimes the orchestrator and sometimes a container inside the orchestration. Target: the test JVM runs as a normal step (`mvn verify`), not as a compose service; the `integration-tests` service is removed.

### 8.4 docker-compose end state

Keep compose for the **custom-application tier** (aggregators + command-adaptor) and local debugging (Kafdrop, Jaeger). Move the **infrastructure tier** (Kafka, Zookeeper, Schema Registry, Redis, LocalStack) to Testcontainers, owned by Maven, for per-run isolation. This is the Section 4 transition plan, now anchored to a single owner.
